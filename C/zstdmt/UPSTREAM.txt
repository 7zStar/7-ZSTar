          (c) 7-ZSTar ONLY -- these will NOT arrive via any upstream merge.
              Each carries a `7-ZSTar:` comment at the site, so
              `git grep -n "7-ZSTar:" C/zstdmt/` lists them all:
                - free(wl) on the wl->out.buf OOM path in pt_compress(),
                  in all four *-mt_compress.c. Upstream left this out of
                  PR #539 on purpose to keep that diff narrow.
                - pthread_mutex_destroy() x2 on BROTLIMT_createDCtx()'s
                  err_cwork path in brotli-mt_decompress.c, needed because
                  (a)'s #538 made the matching init unconditional.
                - *MT_decompressDCtx() checks ctx for NULL before the
                  initializers that dereference it, in all four
                  *-mt_decompress.c. Upstream has this recorded as a known
                  defect but has not sent a fix.
                - realloc() results go through a temporary, and the
                  (buf, allocated) pair is reset together on failure, at
                  both sites in all four *-mt_decompress.c. Also recorded
                  upstream, also unfixed there.
                - brotli's container probe covers the whole 16-byte first
                  frame header (all fixed fields: magic, +4 == 8,
                  +12 == BROTLIMT_MAGICNUMBER), not just the 4-byte magic,
                  and hands every probed byte back to the raw decoder on
                  any mismatch; pt_read()'s frames == 0 case consumes the
                  parked header (ctx->frame0_hdr) instead of re-reading
                  its tail. Narrows the ~2^-32 raw-stream false positive
                  that #541's 4-byte probe left behind to ~2^-80.
                  brotli-mt_decompress.c, plus a @threads doc note in
                  brotli-mt.h. Worth offering upstream only if they keep
                  #541's content detection -- as of 2026-08-05 they are
                  weighing a revert (see #538).
                - BROTLIMT_createDCtx() takes a `threadsset` flag, and
                  (threadsset != 0, threads == 0) forces the raw decoder
                  in BROTLIMT_decompressDCtx() instead of probing the
                  content. This is the escape hatch out of detection, so
                  a raw stream that does collide with the container
                  header stays readable; the entry above only makes such
                  a collision rarer, and upstream's measurements put the
                  hatch, not the probe width, as the load-bearing half
                  (see #538).
                  brotli-mt_decompress.c + brotli-mt.h.
                  Ported from sebres' b4e36ba7 in mcmilk/7-Zip-zstd, but
                  NOT byte-identical to it and deliberately so, twice
                  over: (1) that fork's -mmt=off already arrives as
                  threads == 0 while its unforced case arrives as a real
                  count, so it needs no flag to tell the two apart -- on
                  official 7-Zip both arrive as 0 and the flag is what
                  separates them; (2) sebres also skips detection when a
                  count >= 1 is forced, which would make -mmt=4 decide
                  how a file is read. In mcmilk's fork -mmt selects the
                  brotli format and that follows; here -mmt is official
                  7-Zip's CPU knob, so a forced count is accepted and
                  then ignored by the routing. Same reason this cannot
                  simply be re-vendored if sebres' commit lands upstream:
                  merge it, but keep the routing as it is here.
                  The CPP side narrows it further -- only an explicit
                  -mmt=0 reaches the hatch, not the -mmt=off / -mmt-
                  spellings official 7-Zip also folds onto a forced
                  count of 1, since those cannot be told from -mmt=1 and
                  honouring them would stop that from reading mcmilk's
                  mt containers. That decision lives in
                  CPP/7zip/Archive/BrotliHandler.cpp's ForceRawStream();
                  this directory only sees the resulting pair.
                - Every per-frame size a decoder reads from a header is
                  bounded before it is allocated, against
                  MT_FRAME_SIZE_MAX / MT_FRAME_CSIZE_MAX (256 MiB, plus
                  1/256 for the compressed size), defined in memmt.h
                  with the reasoning: the skippable header's compressed
                  size in all four pt_read(), the LZ4-frame content size
                  in lz4/lz5/lizard pt_decompress() (which also requires
                  the FLG Content Size bit, without which +6 is block
                  data), and brotli's 64 KiB hint, which is now widened
                  to size_t before the shift (the U16 promoted to int
                  overflowed from 0x8000). Out of range is data_error.
                  None of the formats limits a frame, so 256 MiB is a
                  policy: 7-ZSTar and 7-Zip-zstd write <= 4 MiB (brotli
                  <= 11 MiB) per frame, and only zstdmt's CLI with
                  `-b` > 256 writes more. build/testdata/oversize-*
                  pin this (Test-Smoke.ps1). As of 2026-11-03 neither
                  mcmilk/7-Zip-zstd nor mcmilk/zstdmt bounds these
                  fields (zstdmt 0c33b99f only added the in->size < 14
                  check present here).
                  all four *-mt_decompress.c + memmt.h.
                - brotli's st_decompress() writes what decoded before the
                  input ended, then reports end_of_data as it always did.
                  New st_drain_output(): the output buffer first, then the
                  decoder's ring buffer through BrotliDecoderHasMoreOutput()
                  / BrotliDecoderTakeOutput(), because on NEEDS_MORE_INPUT
                  the decoder only pushes what fits in the output buffer.
                  build/testdata/trunc-prefix.br pins it (Test-Smoke.ps1).
                  Not offered upstream yet. brotli-mt_decompress.c.

notes:    Generic block-splitting multi-threading harness (memmt.h, list.h,
          threading.h scaffolding) with one thin per-codec wrapper pair
          each for brotli-mt_*.c, lizard-mt_*.c, lz4-mt_*.c, lz5-mt_*.c
          (compress/decompress/common, 3 files x 4 codecs = 12 files) plus
          zstd-mt_threading.c. zstd itself does *not* use this library --
          zstd's own multithreading (ZSTDMT) is built into C/zstd/ itself
          (zstd_compress's ZSTD_c_nbWorkers parameter, see C/zstd/UPSTREAM.txt
          and CPP/7zip/Compress/ZstdEncoder.cpp) and predates/bypasses this
          wrapper entirely -- zstd-mt_threading.c here is a leftover shared
          threading primitive some of the other four codecs' *-mt_*.c files
          depend on, not zstd-specific glue.
