## Системные требования

**Windows 7 или Windows Server 2008 R2, x64 или x86. На arm64 — Windows 10.**
Больше ничего не нужно: среда выполнения C скомпонована статически (`-MT`), поэтому бинарные файлы импортируют только собственные библиотеки DLL Windows — ни распространяемых пакетов, ни .NET.

Эта нижняя граница *выведена* из того, что требуют пакеты, и проверена на Windows 7 SP1 с установленными более поздними обновлениями (в том числе с PowerShell 5.1), на Windows 10 22H2 и на Windows 11, везде 64-разрядных. На Windows 7 и 10 проверка охватывала установку и удаление `.msi` x64 для всех пользователей и для одного пользователя, мастер установки, `.zip` x64, каждый добавленный кодек и каждый одношаговый формат tar, контекстное меню, ассоциации файлов и файл справки, а также `.msi` и `.zip` x86, запущенные на 64-разрядной Windows. Больше ничего на Windows не проверялось: ни Windows 8 и 8.1, ни Windows Server, ни 32-разрядная Windows, ни оборудование arm64, ни Windows 7 без этих обновлений. Эта граница к тому же выше, чем у исходного 7-Zip, чьи бинарные файлы по-прежнему загружаются в Windows XP. Её определяют три вещи, и вторую не отменит ни один параметр сборки:

- `.msi` объявляет `InstallerVersion="500"`, а Установщик Windows 5.0 поставлялся "with Windows Server 2008 R2 and later and Windows 7 and later" (то есть с Windows Server 2008 R2 и более поздними версиями и с Windows 7 и более поздними версиями) ([Microsoft][msi-versions]). Переносимый `.zip` не использует Установщик Windows, но см. следующие два пункта.
- **zstd и fast-lzma2 используют синхронизацию, появившуюся только в Vista.** Оба принудительно задают `_WIN32_WINNT 0x0600` в собственных заголовках и напрямую вызывают `InitializeConditionVariable` / `SleepConditionVariableCS`, поэтому `7z.dll` и `7za.exe` — два бинарных файла со встроенными кодеками — импортируют четыре функции, которых нет в Windows XP и Server 2003. `7z.dll` из исходного 7-Zip не импортирует ни одной из них.
- Набор инструментов: сборка выполняется в Visual Studio 2022, у которой список поддерживаемых целевых систем — Windows 7 и новее; Vista и Server 2008 помечены как "No" ([Microsoft][vs-targeting]). Версия подсистемы в собранных файлах — 6.0 для x64 и x86 и 6.2 для arm64, а Windows на arm64 в любом случае начинается с Windows 10.

Windows Vista и Server 2008 оказываются посередине: бинарные файлы загрузились бы, но набор инструментов их не поддерживает, установщик там не запустится, и 7-ZSTar на них не проверялся.

**Linux поддерживается только как сборка для командной строки; macOS не поддерживается.**
Форк собирает нативный `7zz` (консольную программу `Alone2`) с помощью gcc через собственный makefile, который подключает makefile исходного проекта и не изменяет ни один из них:
`cd CPP/7zip/Bundles/Alone2 && make -j"$(nproc)" -f makefile.7zstar.gcc`.
Сборка проверялась только на Ubuntu 24.04 с gcc 13.3 (x86-64): она проходит без предупреждений с флагами исходного проекта, проверочный тест из 77 проверок успешно проходит, а 25 векторов совместимости, созданных в Windows, и 37, созданных в Linux, дают те же вердикты, что и в Windows. Два принадлежащих форку файла, затронутых переносом, по-прежнему собираются без изменений в Windows (чистая сборка x64, проверочные тесты и обратное чтение для проверки совместимости проходят). Графического интерфейса нет. Остальные цели Linux исходного проекта (`7za`, `7zr`, `7z.so`) не поддерживаются: в их списках объектных файлов gcc нет того, что нужно изменениям форка в обработчиках исходного проекта, поэтому ожидается, что они не скомпонуются. Другие архитектуры, дистрибутивы и компиляторы не проверялись, а macOS никогда не собирался, поэтому указать `MACOSX_DEPLOYMENT_TARGET` нельзя. Шаги сборки, тесты и известные ограничения описаны в `build/linux/README.md`; совместимость с инструментами Linux — в `test/interop/REPORT.md`.

## Неподписанные пакеты, SmartScreen и Интеллектуальное управление приложениями

**Установщики и программы в выпуске 7-ZSTar не подписаны цифровой подписью центра сертификации**, и у проекта нет сертификата для подписи кода. Поэтому Windows не может определить, кто опубликовал файл, и когда вы впервые запускаете `.msi` или программу из `.zip`, Фильтр SmartScreen в Microsoft Defender может остановить запуск предупреждением. В документации Microsoft для разработчиков "No signature" (нет подписи) названо среди случаев, когда показывается предупреждение с заголовком «Система Windows защитила ваш компьютер» ("Windows protected your PC" в тексте Microsoft), где пользователь должен выбрать «Выполнить в любом случае» ("Run anyway"), прежде чем приложение запустится ([Microsoft][smartscreen-rep]). Корпоративная политика может полностью убрать этот выбор; на таком компьютере обратитесь к тем, кто им управляет.

Единственное, что в выпуске *подписано*, — это небольшой пакет, который помещает 7-ZSTar на первый уровень контекстного меню Windows 11; он находится внутри `.msi` для всех пользователей. Его сертификат самоподписанный и создаётся при сборке именно этого пакета, поэтому это не подпись центра сертификации, и она ничего не говорит о том, кто собрал пакет; что он делает и как от него отказаться, см. в разделе [Контекстное меню Windows 11](#контекстное-меню-windows-11).

Предупреждение не доказывает, что файл плохой, а его отсутствие не доказало бы, что файл хороший. Вы можете сами проверить, что ваша копия — в точности та, что опубликована на странице выпуска. В каждом выпуске есть файл `SHA256SUMS`: по одной строке на пакет — хэш SHA-256, за которым следует имя файла.

1. Скачайте пакет и `SHA256SUMS` с одной и той же страницы выпуска в одну и ту же папку.
2. Откройте PowerShell в этой папке и сравните. Подставьте вместо имени имя скачанного вами файла:

   ```powershell
   $name = '7-ZSTar-26.05.1-x64.msi'
   $expected = ((Get-Content .\SHA256SUMS | Where-Object { $_ -match ([regex]::Escape($name) + '$') }) -split '\s+')[0]
   $actual   = (Get-FileHash -Algorithm SHA256 -LiteralPath $name).Hash
   $actual -eq $expected
   ```

   `True` означает, что хэши совпадают. Чтобы посмотреть их самому, выполните
   `Get-FileHash -Algorithm SHA256 .\7-ZSTar-26.05.1-x64.msi` и найдите то же
   имя файла в `SHA256SUMS`; при сравнении регистр букв не учитывается.
3. Если вы получили `False` или имени файла нет в `SHA256SUMS`, не запускайте его: удалите файл и скачайте снова. Если он по-прежнему не совпадает, сообщите об этом, как описано в [SECURITY.md](../../SECURITY.md).

`SHA256SUMS` охватывает только файлы, загруженные в этот выпуск. Если вы сами соберёте тот же тег, хэши будут другими (пакет контекстного меню подписывается новым сертификатом при каждой сборке); а исходный код публикуется с каждым выпуском, если вы предпочитаете собрать его сами: см. [build/README.md](../../build/README.md).

Когда хэши совпали и вас устраивает происхождение файла:

- **`.msi`** — запустите его как обычно. Если SmartScreen его останавливает, выберите вариант запуска в любом случае («Выполнить в любом случае» в русской версии Windows, "Run anyway" в англоязычной). Окно предупреждения, возможно, сначала придётся развернуть: на проверенном компьютере с Windows 10 в нём была только кнопка «Не выполнять», пока не щёлкнуть ссылку под сообщением. После этого `.msi` для всех пользователей запрашивает одобрение администратора, как любой другой установщик.
- **`.zip`** — распакуйте его и запустите `7zFM.exe` или `7z.exe` из папки. Программы внутри тоже не подписаны, поэтому Windows может показать то же предупреждение при первом запуске каждой из них.

SmartScreen предупреждает, исходя из того, насколько файл известен, а не только из подписей; файл, скачанный немногими людьми, может вызвать предупреждение, даже будучи подписанным. Ничто из описанного здесь этого не меняет, и ни один из шагов выше не отключает SmartScreen.

### Интеллектуальное управление приложениями в Windows 11

На некоторых компьютерах с Windows 11 включена более строгая защита — **Интеллектуальное управление приложениями**. Когда она включена, Windows блокирует неподписанные файлы, если облачная служба Microsoft не может за них поручиться, а у нового выпуска обычно нет такой записи ([Microsoft][sac-faq], [Microsoft][smartscreen-rep]). В отличие от предупреждения SmartScreen, у этой блокировки нет варианта всё же запустить файл, а в часто задаваемых вопросах Microsoft сказано, что обойти Интеллектуальное управление приложениями для отдельного приложения нельзя.

Вот что произошло, когда 7-ZSTar 26.05.1 попробовали на Windows 11 Pro 25H2 (сборка 26200.8037) с включённым Интеллектуальным управлением приложениями:

- **Установщики `.msi` были заблокированы** — и для всех пользователей, и для одного пользователя. В Windows с традиционным китайским языком Установщик Windows показал «系統禁用此安裝。請連絡系統管理員。», а уведомление «Безопасность Windows» сообщило, что Интеллектуальное управление приложениями заблокировало файл, потому что Windows не может определить, кто его опубликовал, и это не известное Windows приложение. Варианта продолжить не было, а `msiexec /i ... /qn` вернул ошибку 1625. Это сообщение — строка 1625 Установщика Windows; в англоязычной Windows та же строка звучит так: "The system administrator has set policies to prevent this installation." (прочитано из английских ресурсов Установщика Windows, на экране не видели).
- **Программа из `.zip` запустилась.** `7zFM.exe`, извлечённый из переносимого `.zip`, в том же тесте запустился нормально. Позволить ли запуск неподписанной программы, Windows решает сама для каждого файла, поэтому на вашем компьютере результат может быть другим.
- Сразу после включения Интеллектуального управления приложениями `.msi` несколько минут устанавливался, прежде чем его начали блокировать. Причину найти не удалось, поэтому успешная установка сразу после включения не означает, что установщик разрешён.

Итак, на компьютере, где Интеллектуальное управление приложениями включено, **установщики установить нельзя**, и проверка `SHA256SUMS` этого не меняет. Меняет другое — отключение Интеллектуального управления приложениями в приложении «Безопасность Windows», в разделе Параметры службы "Интеллектуальное управление приложениями" (в проверенной Windows с традиционным китайским языком: Windows 安全性, 應用程式與瀏覽器控制, 智慧型應用程式控制設定). В тесте выбор варианта «Выключить» вступил в силу сразу, без перезагрузки, и после этого установщики установились. Это параметр для всего компьютера, и ничто здесь не просит вас его менять: решать вам или вашему администратору на управляемом компьютере.

Стоит заранее узнать и то, можно ли включить его обратно. В часто задаваемых вопросах Microsoft сказано, что недавние обновления Windows позволяют снова включить Интеллектуальное управление приложениями без чистой переустановки Windows, поэтому в версии без них отключение может оказаться необратимым. В проверенной здесь сборке вариант включения по-прежнему предлагался после отключения; это результат теста, а не обещание для вашей версии.

## Установка

Три пакета, все собираются скриптом `installer\Build-Package.ps1` (пакет для одного пользователя — с параметром `-PerUser`):

| | `.msi` | `-user.msi` | `.zip` |
|---|---|---|---|
| Устанавливается для | всех учётных записей | учётной записи, которая устанавливает | - |
| Контекстное меню Проводника | да | да, только классическое меню ([ниже](#пакет-для-отдельного-пользователя)) | нет |
| Меню "Пуск": пункт программы | да | да | нет |
| Нужен администратор | да | нет | нет |
| Удаление | *Установленные приложения* в приложении «Настройки» | *Установленные приложения* в приложении «Настройки» | удалить папку |

*Установленные приложения* — название в Windows 11. В Windows 10 та же страница называется *Приложения и возможности*, а в Windows 7 это *Программы и компоненты* в разделе «Панель управления».

Используйте пакеты, которые соответствуют самой Windows: x86 для 32-разрядной Windows, x64 для 64-разрядной, arm64 для Windows на Arm (пакеты arm64 собираются, но ни разу не запускались). Расширение оболочки x86 32-разрядное, и 64-разрядный Проводник не может его загрузить, поэтому в 64-разрядной Windows у x86 `-user.msi` нет контекстного меню вообще, а у x86 `.msi` оно есть только в Windows 11 и только для учётных записей, которые зарегистрировали его пакет для Windows 11 (той, что устанавливала, или той, что выполнила `-Register`, см. ниже).

MSI устанавливается в `Program Files\7-ZSTar` — всегда: в отличие от пакета для одного пользователя, он не предлагает выбор папки и игнорирует `INSTALLFOLDER` в командной строке, потому что в этой папке лежит сценарий, который установщик выполняет от имени SYSTEM, и DLL, которую загружает Проводник каждого пользователя, а папка, созданная в другом месте (например, в `C:\`), доступна для записи всем пользователям. Он регистрирует собственный CLSID расширения оболочки и собственный раздел реестра `Software\7-ZSTar`, а каждому ключу контекстного меню даёт имя `7-ZSTar`, поэтому не пересекается с ключами официального 7-Zip и не удаляет их. См. [installer/GUIDS.md](../../installer/GUIDS.md).

Он запускает обычный мастер установки (welcome, licence, setup type, optional feature tree, finish: приветствие, лицензия, тип установки, дерево необязательных компонентов, завершение), а тихая установка по-прежнему работает без изменений (`msiexec /i 7-ZSTar-<version>-<arch>.msi /qn`), потому что в тихом режиме msiexec пропускает всю последовательность с интерфейсом. Мастер только на английском, в том числе в Windows с другим языком (замечено в Windows 10 с традиционным китайским языком; `.msi` собран без других языков), а на его завершающей странице флажок *Launch 7-ZSTar File Manager* по умолчанию установлен.

### Контекстное меню Windows 11

В Windows 11 пункт находится в меню первого уровня, а не спрятан под пунктом *Показать дополнительные параметры*, где по-прежнему находятся официальный 7-Zip и WinRAR. Windows 11 показывает там расширение оболочки только тогда, когда оно поставляется с удостоверением пакета, поэтому MSI кладёт рядом с программой небольшой пакет MSIX, содержащий только удостоверение, и регистрирует его во время установки. Классическая регистрация тоже сохраняется. Именно она помещает пункт в контекстное меню Windows 10 и Windows 7, у которых меню состоит из одного уровня и нет пункта *Показать дополнительные параметры*, и именно она сохраняет его работоспособность для тех, кто вернул старое контекстное меню.

Этот пакет подписан **самоподписанным сертификатом**, и установщик помещает его в `LocalMachine\TrustedPeople`: Windows не развернёт пакет, подпись которого не восходит к чему-либо доверенному. При удалении сертификат убирается вместе с пакетом. В Windows 10 и Windows 7 установщик не делает ни того, ни другого: он не добавляет сертификат и не регистрирует пакет, а меню обеспечивает одна классическая регистрация.

Если вы предпочитаете не доверять самоподписанному сертификату, откажитесь только от этой части и оставьте всё остальное:

```
msiexec /i 7-ZSTar-<version>-<arch>.msi SPARSE=0
```

Тогда у вас будет только классическое меню, то есть в Windows 11 пункт 7-ZSTar находится в контекстном меню под пунктом *Показать дополнительные параметры*. Чтобы позже включить пункт первого уровня или отменить его после обычной установки:

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -TrustCert -Register
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -Unregister -UntrustCert
```

Доверие к этому сертификату означает, что Windows без предупреждения примет и **любой другой** пакет, подписанный тем же ключом. Он используется только для этого пакета, и при удалении его снова убирают, но именно с этим вы соглашаетесь: `SPARSE=0` выше — способ отказаться.

Регистрация пакета выполняется для каждого пользователя отдельно, а установщик выполняет её только для того, кто устанавливал. Отсюда два следствия:

- Вторая учётная запись на том же компьютере получает только классическое меню, пока не выполнит тот же сценарий с `-Register`.
- Удаление отменяет регистрацию только для того, кто удаляет. Если кто-то другой зарегистрировал пакет, его регистрация переживёт удаление и будет указывать на папку, которой больше нет; эта учётная запись убирает её командой `Get-AppxPackage 7-ZSTar | Remove-AppxPackage`.

**Известное ограничение: меню первого уровня регистрируется только тогда, когда установка выполняется в интерактивном сеансе с выполненным входом.** Если устанавливать `.msi` для всех пользователей из удалённого или неинтерактивного сеанса — по SSH или при тихом развёртывании из средства управления, — установка по-прежнему сообщает об успехе, но пакет для Windows 11 не регистрируется, поэтому появляется только классическое меню под пунктом *Показать дополнительные параметры*. В тесте `msiexec /i ... /qn` из сеанса SSH (сеанс 0) завершился с кодом 0, а `Setup-ShellIntegration.ps1` сообщил `registration failed: 0x80070005` (Отказано в доступе.); тот же `.msi`, установленный из консольного сеанса администратора, зарегистрировался нормально.

`-Status` выводит, что установлено, а что нет.

### Пакет для отдельного пользователя

`7-ZSTar-<version>-<arch>-user.msi` устанавливается только для текущей учётной записи, в `%LOCALAPPDATA%\Programs\7-ZSTar`, без запроса «Контроль учетных записей» (UAC). Всё, что он регистрирует, попадает в `HKCU`; пакет ничего не пишет в `HKLM` (кроме собственного учёта Установщика Windows). Вот что он делает не так, как пакет для компьютера:

- **Нет меню Windows 11 первого уровня.** В Windows 11 7-ZSTar находится в контекстном меню под пунктом *Показать дополнительные параметры*. Для пункта первого уровня нужно, чтобы самоподписанный сертификат был доверенным на всём компьютере, а для этого требуется администратор: измерения в Windows 11 показали, что сертификата в `CurrentUser\TrustedPeople` недостаточно, чтобы Windows развернула пакет. Поэтому пакет для одного пользователя его не включает.
- **Только один из двух на компьютер.** Каждый пакет отказывается устанавливаться, пока установлен другой; удалите один, прежде чем устанавливать другой. Пакет для компьютера видит только копию для одного пользователя в той учётной записи, из которой он запущен, поэтому установка для одного пользователя в другой учётной записи не обнаруживается.
- **Групповая политика может скрыть его меню.** Там, где задан `EnforceShellExtensionSecurity`, Проводник загружает только расширения оболочки, перечисленные в общем для компьютера разделе *Approved*, в который установка для одного пользователя записать не может, поэтому контекстное меню не появляется. Там используйте пакет для компьютера.
- **Очистка формата в Сервис > Настройки > Система также убирает предложение 7-ZSTar для него.** Когда вы очищаете там формат (щёлкайте его ячейку, пока она не станет пустой, затем OK), файловый менеджер целиком удаляет ключи `HKCU\Software\Classes\.<ext>` и `7-ZSTar.<ext>`, а при установке для одного пользователя в этих ключах хранится и то, что пакет зарегистрировал для Настройки > Приложения > Приложения по умолчанию и для списка *Открыть с помощью*. После этого 7-ZSTar пропадает из списка *Открыть с помощью* для этого формата, а в разделе «Приложения по умолчанию» для него показывается пустая запись. Восстановление установки возвращает его (запустите `.msi` ещё раз и выберите *Repair*, то есть восстановить). Лучше назначать типы файлов в разделе «Приложения по умолчанию», а не в файловом менеджере. У пакета для компьютера то же слабое место есть в одном случае, он описан ниже в разделе об ассоциациях файлов.

### Ассоциации файлов и что с ними происходит при удалении

**Задавайте их в Настройки > Приложения > Приложения по умолчанию.** В Windows 11 введите там 7-ZSTar, и будут перечислены все форматы, которые он может открывать, чтобы назначить их. В Windows 10 7-ZSTar указан под *Set defaults by app* (задание значений по умолчанию по приложениям) на этой странице, где *Manage* (управление) показывает его форматы. В Windows 7 нет приложения «Настройки»: 7-ZSTar указан по пути Панель управления > Программы по умолчанию > *Задание программ по умолчанию*, и именно это в данном руководстве подразумевается там под *Приложения по умолчанию*. Назначение форматов с этих двух страниц не проверялось. Установщик регистрирует 7-ZSTar как приложение раздела «Программы по умолчанию» — ProgID для каждого формата с его значком и командой открытия, запись в списке *Открыть с помощью* каждого расширения и блок Capabilities, который читает Windows, — но намеренно не заявляет права ни на один тип файлов: какая программа открывает ваши архивы, решаете вы, и именно это не даёт 7-ZSTar и официальному 7-Zip мешать друг другу. Windows всё же может сама направить формат в 7-ZSTar, когда никакая другая программа не предлагает его открыть: на проверенных компьютерах с Windows 10 и Windows 7, где никто больше не зарегистрировал `.7z`, файл `.7z` показывал значок 7-ZSTar и открывался в нём по двойному щелчку, без вопроса Windows о том, какую программу использовать.

**Сервис > Настройки > Система в файловом менеджере в Windows 11 в основном не работает**, и это правило Windows, а не ошибка здесь. Он записывает ProgID `7-ZSTar.<ext>` в `HKCU\Software\Classes`, а для любого расширения, уже известного компьютеру (а известен каждый формат архивов), Windows 11 его игнорирует: `AssocQueryString` отвечает `Unknown`, и Проводник рисует пустой стандартный значок. Учитывает она вместо этого ключ `UserChoice`, снабжённый хэшем, который может вычислить только сама Windows, поэтому там единственный путь — интерфейс «Настройки». Записать такой ключ не может ни одно приложение: ни 7-ZSTar, ни 7-Zip, ни какой-либо установщик. Windows 10 и Windows 7 в тестах вели себя иначе: когда `.7z` и `.zst` были заданы в файловом менеджере и никакая другая программа для них не выбиралась, `AssocQueryString` возвращал для обоих `7zFM.exe`.

**Очистка формата в столбце *Все пользователи* убирает собственную регистрацию пакета для компьютера для этого формата.** Этот столбец записывает в `HKLM\Software\Classes`, где пакет для компьютера хранит ProgID и записи *Открыть с помощью*, которые он предлагает, и очистка формата там (для неё файловый менеджер нужно запустить командой «Запуск от имени администратора») целиком удаляет эти ключи — для всех учётных записей. Восстановление вернуло те же ключи для пакета для одного пользователя; для этого пакета это не измерялось.

**Значок, который остаётся пустым после любых изменений,** может объясняться и кэшем значков Проводника, который не замечает, что уже занесённая в кэш DLL заменена; `ie4uinit.exe -show` очищает его ненадёжно. Закройте Проводник, удалите `%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db`, запустите его снова.

**Удаление убирает те ассоциации, до которых может дотянуться** — ProgID `7-ZSTar.*` того, кто удаляет, и только те типы файлов, которые всё ещё на них указывают, поэтому формат, который тем временем передали другой программе, остаётся нетронутым. Удаление пакета для компьютера также не трогает ProgID, который открывает копию 7-ZSTar, всё ещё существующую где-то в другом месте, — переносимую из `.zip`, настроенную собственным **Сервис > Настройки > Система** этой копии. Пакет для одного пользователя так не может: его ProgID — это те самые ключи `HKCU` (см. *Пакет для отдельного пользователя* выше), и при его удалении они удаляются, кто бы ни записал их последним. Если оставить их, эти типы указывали бы на ProgID, значок и команда которого — удалённый исполняемый файл, то есть пустой значок и ошибка при двойном щелчке. Ассоциации других учётных записей недосягаемы; они могут очистить свои сами командой `Setup-ShellIntegration.ps1 -RemoveAssociations` до того, как программа будет удалена. `msiexec /x ... KEEPASSOC=1` пропускает этот шаг, а обновление никогда его не выполняет.

**Известное ограничение: другие учётные записи сохраняют ассоциации, которые задали сами.** Удаление пакета для компьютера очищает только то, что учётная запись, выполняющая удаление, задала в своём столбце (озаглавленном именем учётной записи) в разделе **Сервис > Настройки > Система** файлового менеджера. Любая другая учётная запись, задавшая там ассоциации, сохраняет их, и они указывают на удалённую программу, поэтому при двойном щелчке по файлу `.7z` Windows спрашивает, какую программу использовать. Каждой учётной записи следует очистить свои **до** удаления командой

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -RemoveAssociations
```

которая убирает только записи 7-ZSTar, либо потом назначить типы заново в Настройки > Приложения > Приложения по умолчанию. Если делать это в файловом менеджере, нужно щёлкать каждую ячейку в своём столбце, где показан 7-ZSTar, пока она не станет пустой, затем OK; не выделяйте все строки и не нажимайте "+": это применяет одно состояние ко всем выделенным строкам и поэтому очищает и форматы, принадлежащие другой программе, например официальному 7-Zip.

Ассоциации, заданные в столбце **Все пользователи**, очистка при удалении не затрагивает вообще, и каждая учётная запись остаётся указывающей на удалённую программу. Администратор, задавший какие-либо из них, должен очистить эти ячейки в файловом менеджере, запущенном командой «Запуск от имени администратора», затем OK — до удаления; `-RemoveAssociations` до этого столбца не дотягивается. Очистка его непосредственно перед удалением безвредна, хотя она удаляет там собственную регистрацию пакета (см. выше), поскольку удаление всё равно её убирает. У пакета для одного пользователя проблемы с другими учётными записями нет, а официальный 7-Zip ведёт себя так же.

## Языки

Каждый пакет содержит переводы исходного проекта — чуть более 90 языков. Выберите язык в **Сервис > Настройки > Язык**; MSI также позволяет не включать их при установке *Custom*. 7-ZSTar при первом запуске пытается следовать языку системы, но это определение отказывается и остаётся на английском, когда в Windows не совпадают параметр «Язык программ, не поддерживающих Юникод» и параметр «Формат региона»: выбор языка вручную работает всегда.

Строки, добавленные самим 7-ZSTar, — поля уровня и словаря zstd, названия новых форматов архивов — не имеют перевода из исходного проекта и остаются на английском. Исключение — кнопки **Поддержать** и **Сайт** в окне «О программе»: для каждой из них есть слово в 67 из 92 языков, а в остальных 25 показывается английское (`Lang/UPSTREAM.md` перечисляет их).
Переводы взяты из исходного проекта как есть, здесь они не пишутся: см. [Lang/UPSTREAM.md](../../Lang/UPSTREAM.md).
