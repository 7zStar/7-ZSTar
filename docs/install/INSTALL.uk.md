## Системні вимоги

**Windows 7 або Windows Server 2008 R2, x64 або x86. На arm64 — Windows 10.**
Більше нічого не потрібно: середовище виконання C зв'язане статично (`-MT`), тож виконувані файли імпортують лише власні DLL-бібліотеки Windows — жодних розповсюджуваних пакетів, жодного .NET.

Цю нижню межу *виведено* з вимог самих пакетів, а також перевірено на Windows 7 SP1 з установленими пізнішими оновленнями (серед них PowerShell 5.1), Windows 10 22H2 і Windows 11 — усі 64-розрядні. У Windows 7 і 10 перевірялося таке: установлення та видалення x64 `.msi` для всіх користувачів і для окремого користувача, майстер встановлення, x64 `.zip`, усі додані кодеки та формати tar в один крок, контекстне меню, асоціації файлів і файл довідки, а також робота x86 `.msi` і `.zip` у 64-розрядній Windows. Нічого іншого у Windows не перевірялося: ні Windows 8 чи 8.1, ні Windows Server, ні 32-розрядної Windows, ні апаратного забезпечення arm64, ні Windows 7 без згаданих оновлень. Ця межа також вища, ніж у вихідного 7-Zip, чиї виконувані файли досі завантажуються у Windows XP. До неї призводять три речі, і друга з них така, яку не скасує жоден параметр збирання:

- `.msi` оголошує `InstallerVersion="500"`, а Інсталятор Windows 5.0 постачався, як сказано в документації, «with Windows Server 2008 R2 and later and Windows 7 and later» ([Microsoft][msi-versions]). Портативний `.zip` не використовує Інсталятора Windows, але див. наступні два пункти.
- **zstd і fast-lzma2 використовують синхронізацію, доступну лише з Vista.** Обидва в своїх заголовках примусово задають `_WIN32_WINNT 0x0600` і напряму викликають `InitializeConditionVariable` / `SleepConditionVariableCS`, тому `7z.dll` і `7za.exe` — два файли з вбудованими кодеками — імпортують чотири функції, яких немає у Windows XP і Server 2003. `7z.dll` вихідного 7-Zip не імпортує жодної з них.
- Інструментарій: файли зібрано у Visual Studio 2022, у списку підтримуваних цільових платформ якого — Windows 7 і новіші; для Vista і Server 2008 там стоїть «No» ([Microsoft][vs-targeting]). Версія підсистеми в зібраних файлах — 6.0 для x64 і x86 та 6.2 для arm64, а Windows на arm64 у будь-якому разі починається з Windows 10.

Windows Vista і Server 2008 опиняються посередині: виконувані файли завантажилися б, але інструментарій їх не підтримує, інсталятор там не запуститься, а 7-ZSTar на них не перевірявся.

**Linux підтримується лише як збирання для командного рядка; macOS не підтримується.**
Форк збирає рідний `7zz` (консольну програму `Alone2`) за допомогою gcc через власний makefile, який підключає makefile вихідного 7-Zip і не змінює жодного з них:
`cd CPP/7zip/Bundles/Alone2 && make -j"$(nproc)" -f makefile.7zstar.gcc`.
Збирання й перевірка проводилися лише в Ubuntu 24.04 з gcc 13.3 (x86-64): збирання проходить без попереджень із прапорцями вихідного 7-Zip, димовий тест із 77 перевірок успішний, а 25 векторів сумісності, створених у Windows, і 37, створених у Linux, дають ті самі вердикти, що й у Windows. Два файли, що належать форку й були змінені під цей порт, як і раніше збираються у Windows без змін (чисте збирання x64, димові тести та зворотне читання сумісності проходять). Графічного інтерфейсу немає. Інші цілі Linux вихідного 7-Zip (`7za`, `7zr`, `7z.so`) не підтримуються: у їхніх списках об'єктних файлів gcc бракує того, що потрібне змінам форку в обробниках вихідного 7-Zip, тож очікується, що вони не зберуться на етапі компонування. Інші архітектури, дистрибутиви й компілятори не перевірялися, а macOS ніколи не збирався, тому вказати `MACOSX_DEPLOYMENT_TARGET` неможливо. Кроки збирання, тести та відомі обмеження описано в `build/linux/README.md`; сумісність з інструментами Linux — у `test/interop/REPORT.md`.

## Непідписані пакети, SmartScreen та Інтелектуальне керування програмами

**Інсталятори та програми у випуску 7-ZSTar не мають підпису коду від центру сертифікації**, і в проєкту немає сертифіката для підпису коду. Тому Windows не може визначити, хто опублікував файл, і під час першого запуску `.msi` або програми з `.zip` Фільтр SmartScreen для Microsoft Defender може зупинити його попередженням. У документації Microsoft для розробників «No signature» названо одним із випадків, коли показується попередження із заголовком «ОС Windows захистила цей ПК» (Windows protected your PC), де користувач має вибрати «Виконати» (Run anyway), перш ніж програма запуститься ([Microsoft][smartscreen-rep]). Політика підприємства може взагалі прибрати цей вибір; на такому ПК зверніться до того, хто ним керує.

Єдине, що у випуску *підписано*, — це невеликий пакет, який розміщує 7-ZSTar на першому рівні контекстного меню Windows 11; він міститься всередині `.msi` для всіх користувачів. Його сертифікат самопідписаний і створюється під час збирання саме цього пакета, тож це не підпис центру сертифікації, і він нічого не говорить про те, хто зібрав пакет; що він робить і як від нього відмовитися, див. у розділі [контекстне меню Windows 11](#контекстне-меню-windows-11).

Попередження не доводить, що файл поганий, а його відсутність не довела б, що файл хороший. Ви можете самостійно перевірити, що ваша копія — саме та, яку опубліковано на сторінці випуску. До кожного випуску додається файл `SHA256SUMS`: по одному рядку на пакет — хеш SHA-256, за яким іде назва файлу.

1. Завантажте пакет і `SHA256SUMS` з тієї самої сторінки випуску в одну й ту саму теку.
2. Відкрийте PowerShell у цій теці й порівняйте. Замініть назву на назву завантаженого вами файлу:

   ```powershell
   $name = '7-ZSTar-26.05.1-x64.msi'
   $expected = ((Get-Content .\SHA256SUMS | Where-Object { $_ -match ([regex]::Escape($name) + '$') }) -split '\s+')[0]
   $actual   = (Get-FileHash -Algorithm SHA256 -LiteralPath $name).Hash
   $actual -eq $expected
   ```

   `True` означає, що хеші збігаються. Щоб переглянути їх самостійно, виконайте `Get-FileHash -Algorithm SHA256 .\7-ZSTar-26.05.1-x64.msi` і знайдіть у `SHA256SUMS` рядок із тією самою назвою файлу; регістр літер під час порівняння не враховується.
3. Якщо ви отримали `False` або назви файлу немає в `SHA256SUMS`, не запускайте його: видаліть файл і завантажте знову. Якщо хеші й надалі не збігаються, повідомте про це, як описано в [SECURITY.md](../../SECURITY.md).

`SHA256SUMS` охоплює лише файли, завантажені до цього випуску. Якщо зібрати той самий тег самостійно, хеші будуть іншими (пакет контекстного меню підписується новим сертифікатом щоразу під час збирання), а вихідний код публікується разом з кожним випуском, якщо ви волієте зібрати програму самі: див. [build/README.md](../../build/README.md).

Коли хеші збігаються й вас влаштовує, звідки взято файл:

- **`.msi`** — запустіть як зазвичай. Якщо SmartScreen його зупинить, виберіть варіант, що дозволяє запустити файл попри попередження («Виконати»; «Run anyway» в англомовній Windows). Вікно попередження, можливо, спершу потрібно розгорнути: на перевіреному комп'ютері з Windows 10 у ньому була лише кнопка, що забороняє запуск файлу, доки не клацнути посилання під повідомленням. Після цього `.msi` для всіх користувачів просить підтвердження адміністратора, як і будь-який інший інсталятор.
- **`.zip`** — розпакуйте його й запустіть `7zFM.exe` або `7z.exe` з теки. Програми всередині теж не підписані, тож під час першого запуску кожної з них Windows може показати таке саме попередження.

SmartScreen зважає на те, наскільки файл відомий, а не лише на підписи; файл, який завантажило мало людей, може викликати попередження, навіть якщо він підписаний. Ніщо з описаного тут цього не змінює, і жоден із наведених вище кроків не вимикає SmartScreen.

### Інтелектуальне керування програмами у Windows 11

На деяких ПК з Windows 11 увімкнено суворіший захист — **Інтелектуальне керування програмами**. Коли його ввімкнено, Windows блокує непідписані файли, якщо хмарна служба Microsoft не може за них поручитися, а для нового випуску такого запису зазвичай немає ([Microsoft][sac-faq], [Microsoft][smartscreen-rep]). На відміну від попередження SmartScreen, у цього блокування немає варіанта все одно запустити файл, а в FAQ Microsoft сказано, що обійти функцію «Інтелектуальне керування програмами» для окремої програми неможливо.

Що сталося, коли 7-ZSTar 26.05.1 випробували на Windows 11 Pro 25H2 (збірка 26200.8037) з увімкненою функцією «Інтелектуальне керування програмами»:

- **Інсталятори `.msi` було заблоковано** — і для всіх користувачів, і для окремого користувача. У Windows із традиційною китайською Інсталятор Windows показав «系統禁用此安裝。請連絡系統管理員。», а сповіщення «Безпека у Windows» повідомило, що функція «Інтелектуальне керування програмами» заблокувала файл, бо Windows не може визначити, хто його опублікував, і це не програма, яку знає Windows. Варіанта продовжити не було, а `msiexec /i ... /qn` повернув помилку 1625. Це повідомлення — рядок 1625 Інсталятора Windows; в англомовній Windows той самий рядок звучить так: «The system administrator has set policies to prevent this installation.» (прочитано з англомовних ресурсів Інсталятора Windows, на екрані не бачили).
- **Програма з `.zip` запустилася.** `7zFM.exe`, розпакований із портативного `.zip`, у тому самому тесті запустився нормально. Чи дозволить Windows запустити непідписану програму, вирішує сама Windows, оцінюючи цей файл, тож на вашому ПК результат може бути іншим.
- Одразу після ввімкнення функції «Інтелектуальне керування програмами» `.msi` кілька хвилин встановлювався, перш ніж його почали блокувати. Причину не знайдено, тож успішне встановлення відразу після ввімкнення не означає, що інсталятор дозволено.

Отже, на ПК, де функцію «Інтелектуальне керування програмами» ввімкнено, **встановлення за допомогою інсталяторів неможливе**, і перевірка `SHA256SUMS` цього не змінює. Змінює це вимкнення функції «Інтелектуальне керування програмами» в розділі «Параметри інтелектуального керування програмами» застосунку «Безпека у Windows» (у перевіреній Windows із традиційною китайською: Windows 安全性, 應用程式與瀏覽器控制, 智慧型應用程式控制設定). У тесті вибір параметра «Вимкнути» набув чинності негайно, без перезавантаження, і після цього інсталятори встановилися. Це параметр для всього ПК, і ніщо тут не просить вас його змінювати: рішення за вами, а на керованому ПК — за вашим адміністратором.

Варто заздалегідь знати й те, чи можна її ввімкнути знову. У FAQ Microsoft сказано, що останні оновлення Windows дозволяють знову ввімкнути функцію «Інтелектуальне керування програмами» без чистого встановлення Windows, тож на версії без цих оновлень вимкнення може бути остаточним. У перевіреній тут збірці параметр її ввімкнення після вимкнення залишався доступним; це результат тесту, а не обіцянка щодо вашої версії.

## Встановлення

Три пакети, усі збираються скриптом `installer\Build-Package.ps1` (пакет для окремого користувача — з параметром `-PerUser`):

| | `.msi` | `-user.msi` | `.zip` |
|---|---|---|---|
| Для кого встановлюється | для всіх облікових записів | для облікового запису, що встановлює | - |
| Контекстне меню у Файловому провіднику | так | так, лише класичне меню ([нижче](#пакет-для-окремого-користувача)) | ні |
| Запис у Меню "Пуск" | так | так | ні |
| Потрібні права адміністратора | так | ні | ні |
| Видалення | *Інстальовані програми* в «Налаштування» | *Інстальовані програми* в «Налаштування» | видаліть теку |

*Інстальовані програми* — це назва в Windows 11. У Windows 10 та сама сторінка називається *Програми та функції*, а в Windows 7 це *Programs and Features* (програми та компоненти) у Control Panel (панель керування).

Використовуйте пакети, що відповідають самій Windows: x86 — для 32-розрядної Windows, x64 — для 64-розрядної, arm64 — для Windows on Arm (пакети arm64 зібрано, але жодного разу не запускали). Розширення оболонки x86 є 32-розрядним, і 64-розрядний Файловий провідник не може його завантажити, тому в 64-розрядній Windows `-user.msi` для x86 узагалі не має контекстного меню, а `.msi` для x86 має його лише в Windows 11 і лише для облікових записів, які зареєстрували його пакет для Windows 11 (того, що встановлює, або того, що виконав `-Register`, див. нижче).

MSI встановлюється в `Program Files\7-ZSTar` — завжди: на відміну від пакета для окремого користувача, він не пропонує вибрати теку й ігнорує `INSTALLFOLDER` у командному рядку, бо ця тека містить скрипт, який інсталятор запускає від імені SYSTEM, і DLL, яку завантажує Файловий провідник кожного користувача, а тека, створена деінде (наприклад, у `C:\`), доступна для запису всім користувачам. Він реєструє власний CLSID розширення оболонки та власний розділ реєстру `Software\7-ZSTar`, а кожен ключ контекстного меню називає `7-ZSTar`, тому не конфліктує з ключами офіційного 7-Zip і не видаляє їх. Див. [installer/GUIDS.md](../../installer/GUIDS.md).

Він запускає звичайний майстер встановлення — *welcome, licence, setup type, optional feature tree, finish* (вітання, ліцензія, тип встановлення, дерево необов'язкових компонентів, завершення), — а тихе встановлення працює без змін (`msiexec /i 7-ZSTar-<version>-<arch>.msi /qn`), бо в тихому режимі msiexec пропускає всю послідовність інтерфейсу. Майстер доступний лише англійською, також і в Windows з іншою мовою інтерфейсу (це бачили в китайській Windows 10 з традиційним письмом; `.msi` зібрано без інших мов), а на його завершальній сторінці за замовчуванням позначено *Launch 7-ZSTar File Manager* (запустити файловий менеджер 7-ZSTar).

### Контекстне меню Windows 11

У Windows 11 пункт розташований у меню першого рівня, а не захований у пункті *Показати додаткові параметри*, де досі містяться офіційний 7-Zip і WinRAR. Windows 11 показує там розширення оболонки лише тоді, коли воно постачається з ідентичністю пакета, тому MSI містить поряд із програмою невеликий пакет MSIX, що несе лише ідентичність, і реєструє його під час встановлення. Класичну реєстрацію також збережено. Саме вона додає пункт до контекстного меню в Windows 10 і Windows 7, у яких меню має один рівень і не має пункту *Показати додаткові параметри*, і саме вона забезпечує його роботу для тих, хто повернув старе контекстне меню.

Цей пакет підписано **самопідписаним сертифікатом**, і інсталятор поміщає його в `LocalMachine\TrustedPeople` — Windows не розгорне пакет, підпис якого неможливо пов'язати з чимось довіреним. Видалення прибирає сертифікат разом із пакетом. У Windows 10 і Windows 7 інсталятор не робить ні того, ні іншого: він не додає сертифіката й не реєструє пакета, а меню забезпечує лише класична реєстрація.

Якщо ви не хочете довіряти самопідписаному сертифікату, відмовтеся лише від цієї частини, а решту залиште:

```
msiexec /i 7-ZSTar-<version>-<arch>.msi SPARSE=0
```

Тоді ви отримаєте лише класичне меню, тож у Windows 11 пункт 7-ZSTar буде в контекстному меню в розділі *Показати додаткові параметри*. Щоб увімкнути пункт першого рівня пізніше або скасувати його після звичайного встановлення:

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -TrustCert -Register
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -Unregister -UntrustCert
```

Довіра до цього сертифіката означає, що Windows також без попередження прийматиме **будь-який інший** пакет, підписаний тим самим ключем. Він використовується лише для цього одного пакета, а видалення прибирає його, але саме на це ви погоджуєтеся: відмовитися від цього можна за допомогою `SPARSE=0`, наведеного вище.

Реєстрація пакета виконується для окремого користувача, і інсталятор виконує її лише для того, хто встановлював. Два наслідки:

- Другий обліковий запис на тому самому комп'ютері отримує лише класичне меню, доки не виконає той самий скрипт із параметром `-Register`.
- Видалення скасовує реєстрацію лише для того, хто видаляє. Якщо пакет зареєстрував хтось інший, його реєстрація переживе видалення й вказуватиме на теку, якої вже немає; цей обліковий запис очищає її командою `Get-AppxPackage 7-ZSTar | Remove-AppxPackage`.

**Відоме обмеження: меню першого рівня реєструється лише тоді, коли встановлення виконується в інтерактивному сеансі, у який виконано вхід.** Установлення `.msi` для всіх користувачів із віддаленого або неінтерактивного сеансу — через SSH чи під час тихого розгортання з інструмента керування — як і раніше повідомляє про успіх, але пакет для Windows 11 не реєструється, тож з'являється лише класичне меню в розділі *Показати додаткові параметри*. У тесті `msiexec /i ... /qn` із сеансу SSH (сеанс 0) завершився з кодом 0, тоді як `Setup-ShellIntegration.ps1` повідомив `registration failed: 0x80070005` (доступ заборонено); той самий `.msi`, встановлений із консольного сеансу адміністратора, зареєструвався нормально.

`-Status` виводить, що наявне, а чого немає.

### Пакет для окремого користувача

`7-ZSTar-<version>-<arch>-user.msi` встановлюється лише для поточного облікового запису в `%LOCALAPPDATA%\Programs\7-ZSTar` без запиту служби захисту користувачів. Усе, що він реєструє, потрапляє в `HKCU`; пакет нічого не записує в `HKLM` (крім власного обліку Інсталятора Windows). Чого він не робить так, як пакет для всього комп'ютера:

- **Немає меню першого рівня Windows 11.** У Windows 11 7-ZSTar міститься в контекстному меню в розділі *Показати додаткові параметри*. Для пункту першого рівня потрібно, щоб самопідписаному сертифікату довіряла вся система, а для цього потрібні права адміністратора: вимірювання в Windows 11 показало, що сертифіката в `CurrentUser\TrustedPeople` недостатньо, щоб Windows розгорнула пакет. Тому пакет для окремого користувача його не містить.
- **Лише один із двох на комп'ютері.** Кожен пакет відмовляється встановлюватися, поки встановлено інший; перш ніж встановлювати інший, видаліть один. Пакет для всього комп'ютера бачить лише копію для окремого користувача того облікового запису, з якого його запущено, тож встановлення для окремого користувача в іншому обліковому записі не виявляється.
- **Групова політика може приховати його меню.** Там, де задано `EnforceShellExtensionSecurity`, Файловий провідник завантажує лише ті розширення оболонки, що перелічені в ключі *Approved* для всього комп'ютера, а встановлення для окремого користувача не може туди записувати, тож контекстне меню не з'являється. Там використовуйте пакет для всього комп'ютера.
- **Очищення формату в розділі Інструменти > Налаштування... > Система також прибирає пропозицію 7-ZSTar для нього.** Коли ви очищаєте там формат (клацайте його клітинку, доки вона не стане порожньою, потім OK), файловий менеджер видаляє цілі ключі `HKCU\Software\Classes\.<ext>` і `7-ZSTar.<ext>`, а для встановлення для окремого користувача в цих ключах зберігається й те, що пакет зареєстрував для Налаштування > Програми > Програми за замовчуванням і для списку *Відкрити за допомогою*. Тоді 7-ZSTar зникає зі списку *Відкрити за допомогою* для цього формату, а в «Програми за замовчуванням» для нього з'являється порожній запис. Відновлення встановлення повертає все назад (запустіть `.msi` ще раз і виберіть *Repair*). Краще призначати типи файлів у «Програми за замовчуванням», а не у файловому менеджері. У пакета для всього комп'ютера є таке саме вразливе місце в одному випадку — його описано нижче в розділі про асоціації файлів.

### Асоціації файлів і що з ними робить видалення

**Налаштовуйте їх у Налаштування > Програми > Програми за замовчуванням.** У Windows 11 введіть там 7-ZSTar, і буде показано всі формати, які він може відкривати, щоб ви їх призначили. У Windows 10 7-ZSTar указано на цій сторінці в розділі *Set defaults by app* (типові значення за застосунком), де *Manage* (кнопка керування) показує його формати. У Windows 7 немає застосунку «Налаштування»: 7-ZSTar указано в Control Panel (панель керування) > Програми за замовчуванням > *Установити програми за замовчуванням*, і саме це в цьому посібнику означає *Програми за замовчуванням* для неї. Призначення форматів із цих двох сторінок не перевірялося. Інсталятор реєструє 7-ZSTar як програму з розділу «Програми за замовчуванням» — ProgID для кожного формату з його піктограмою та командою відкриття, запис у списку *Відкрити за допомогою* для кожного розширення та блок Capabilities, який читає Windows, — але свідомо не претендує на жоден тип файлів: яка програма відкриває ваші архіви, вирішуєте ви, і саме це не дає 7-ZSTar та офіційному 7-Zip заважати одне одному. Windows усе ж може сама відправити формат у 7-ZSTar, коли жодна інша програма не пропонує його відкривати: на перевірених комп'ютерах із Windows 10 і Windows 7, де `.7z` більше ніхто не зареєстрував, файл `.7z` показував піктограму 7-ZSTar і відкривався в ньому подвійним клацанням, і Windows не питала, якою програмою його відкрити.

**Розділ Інструменти > Налаштування... > Система у файловому менеджері у Windows 11 здебільшого не працює**, і це правило Windows, а не помилка тут. Він записує ProgID `7-ZSTar.<ext>` у `HKCU\Software\Classes`, а для будь-якого розширення, яке комп'ютер уже знає (а знає він кожен формат архівів), Windows 11 його ігнорує: `AssocQueryString` відповідає `Unknown`, а Файловий провідник малює порожню типову піктограму. Натомість Windows шанує ключ `UserChoice`, позначений хешем, який може обчислити лише вона сама, тому інтерфейс застосунку «Налаштування» там — єдиний шлях. Жодна програма не може його записати: ні 7-ZSTar, ні 7-Zip, ні будь-який інсталятор. У Windows 10 і Windows 7 під час тестування все було інакше: коли `.7z` і `.zst` було задано у файловому менеджері, а іншу програму для них не вибирали, `AssocQueryString` повертав для обох `7zFM.exe`.

**Очищення формату в стовпці *Усі користувачі* прибирає власну реєстрацію пакета для всього комп'ютера для цього формату.** Цей стовпець записує в `HKLM\Software\Classes`, де пакет для всього комп'ютера зберігає ProgID і записи *Відкрити за допомогою*, які він пропонує, а очищення формату там (для чого файловий менеджер потрібно запускати через *Запустити з правами адміністратора*) повністю видаляє ці ключі — для всіх облікових записів. Відновлення повернуло ті самі ключі для пакета для окремого користувача; для цього пакета це не вимірювали.

**Піктограма, що залишається порожньою після будь-яких змін,** може бути також справою кешу піктограм Файлового провідника, який не помічає, що вже кешовану DLL замінено; `ie4uinit.exe -show` не гарантує його очищення. Закрийте Файловий провідник, видаліть `%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db`, запустіть його знову.

**Видалення прибирає асоціації, до яких може дотягнутися**: ProgID `7-ZSTar.*`, що належать тому, хто видаляє, і лише ті типи файлів, які все ще вказують на них, тож формат, переданий тим часом іншій програмі, лишається недоторканим. Видалення пакета для всього комп'ютера також не чіпає ProgID, який відкриває копію 7-ZSTar десь в іншому місці, що ще існує, — портативну з `.zip`, налаштовану через **Інструменти > Налаштування... > Система** самої цієї копії. Пакет для окремого користувача так не може: його ProgID — це ті самі ключі `HKCU` (див. *Пакет для окремого користувача* вище), і видалення прибирає їх, хоч би хто записав їх останнім. Якби їх залишити, ці типи вказували б на ProgID, піктограма й команда якого — видалений виконуваний файл, тобто порожня піктограма й помилка після подвійного клацання. Асоціації інших облікових записів поза досяжністю; вони можуть очистити власні командою `Setup-ShellIntegration.ps1 -RemoveAssociations` до видалення програми. `msiexec /x ... KEEPASSOC=1` пропускає це, а оновлення ніколи цього не робить.

**Відоме обмеження: інші облікові записи зберігають асоціації, які задали самі.** Видалення пакета для всього комп'ютера очищає лише те, що обліковий запис, який виконує видалення, задав у власному стовпці (заголовок стовпця — ім'я облікового запису) у розділі **Інструменти > Налаштування... > Система** файлового менеджера. Будь-який інший обліковий запис, що задав там асоціації, зберігає їх, і вони вказують на вилучену програму, тож подвійне клацання файлу `.7z` змушує Windows питати, якою програмою його відкрити. Кожному обліковому запису слід очистити свої **до** видалення командою

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -RemoveAssociations
```

яка прибирає лише записи 7-ZSTar, або потім знову призначити типи в Налаштування > Програми > Програми за замовчуванням. Якщо робити це у файловому менеджері, потрібно клацати кожну клітинку у власному стовпці, що показує 7-ZSTar, доки вона не стане порожньою, потім OK; не вибирайте всі рядки й не натискайте «+», бо це застосовує один стан до кожного вибраного рядка і тому очищає також формати, що належать іншій програмі, наприклад офіційному 7-Zip.

Асоціації, задані в стовпці **Усі користувачі**, очищення під час видалення взагалі не чіпає, і вони залишаються такими, що для всіх облікових записів вказують на вилучену програму. Адміністратор, який задав такі асоціації, має очистити ці клітинки з файлового менеджера, запущеного через *Запустити з правами адміністратора*, потім OK, до видалення; `-RemoveAssociations` до цього стовпця не дотягується. Очистити його безпосередньо перед видаленням нешкідливо, хоча це видаляє власну реєстрацію пакета там (див. вище), бо видалення однаково її прибирає. У пакета для окремого користувача проблеми інших облікових записів немає, і офіційний 7-Zip поводиться так само.

## Мови

Кожен пакет містить переклади вихідного 7-Zip — понад 90 мов. Виберіть мову в розділі **Інструменти > Налаштування... > Мова**; MSI також дає змогу не встановлювати їх у режимі встановлення *Custom* (користувацьке). Під час першого запуску 7-ZSTar намагається дотримуватися мови системи, але це визначення здається й залишає англійську, коли «language for non-Unicode programs» у Windows (мова для програм, що не підтримують Юнікод) і параметр «Регіональний формат» не збігаються; вибір мови вручну працює завжди.

Рядки, які 7-ZSTar додав сам, — поля рівня та словника zstd, назви нових форматів архівів — не мають перекладу у вихідному 7-Zip і залишаються англійською. Виняток — кнопки **Підтримати** та **Вебсайт** у діалоговому вікні «Про 7-ZSTar...»: у 67 із 92 мов для обох є переклад, в інших 25 відображається англійська (їх перелічено в `Lang/UPSTREAM.md`). Переклади взято готовими з вихідного 7-Zip, а не написано тут: див. [Lang/UPSTREAM.md](../../Lang/UPSTREAM.md).
