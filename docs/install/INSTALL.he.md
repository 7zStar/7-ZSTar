## דרישות מערכת

‏**⁦Windows 7⁩ או ⁦Windows Server 2008 R2⁩, בארכיטקטורת ⁦x64⁩ או ⁦x86.⁩ ב־⁦arm64⁩: ⁦Windows 10.⁩**
אין צורך בשום דבר נוסף: ספריית זמן הריצה של C מקושרת סטטית (`-MT`), ולכן הקבצים הבינאריים מייבאים רק DLL של Windows עצמו – בלי חבילת הפצה מחדש (redistributable) ובלי .⁦NET.⁩

רף המינימום הזה *נגזר* ממה שהחבילות דורשות, והוא נבדק ב־⁦Windows 7 SP1⁩ עם עדכונים מאוחרים יותר (ביניהם ⁦PowerShell 5.1⁩), ב־⁦Windows 10 22H2⁩ וב־⁦Windows 11⁩, כולם ב־⁦64⁩ סיביות. ב־⁦Windows 7⁩ וב־⁦Windows 10⁩ הבדיקה כללה התקנה והסרה של קובצי `.msi` מסוג ⁦x64⁩ לכל המשתמשים ולמשתמש יחיד, את אשף ההתקנה, את קובץ ה־`.zip` של ⁦x64⁩, כל מקודד (codec) שנוסף וכל תבנית tar בצעד אחד, את תפריט הלחיצה הימנית, שיוכי קבצים וקובץ העזרה, וכן את קובצי ה־`.msi` וה־`.zip` של ⁦x86⁩ כשהם פועלים ב־Windows של ⁦64⁩ סיביות. שום דבר אחר לא נבדק ב־Windows: לא ⁦Windows 8⁩ או ⁦8.1⁩, לא Windows Server, לא Windows של ⁦32⁩ סיביות, לא חומרת ⁦arm64⁩ ולא ⁦Windows 7⁩ בלי אותם עדכונים. הרף גם גבוה מזה של ⁦7-Zip⁩ המקורי (upstream), שהקבצים הבינאריים שלו עדיין נטענים ב־⁦Windows XP.⁩ שלושה דברים מציבים אותו שם, והשני הוא זה שאף הגדרת בנייה אינה יכולה לבטל:

- קובץ ה־`.msi` מצהיר על `InstallerVersion="500"`, ו־⁦Windows Installer 5.0⁩ סופק “⁦with Windows Server 2008 R2 and later and Windows 7 and later⁩” ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/msi/released-versions-of-windows-installer)). קובץ ה־`.zip` הנייד אינו עובר דרך Windows Installer, אבל ראו את שתי הנקודות הבאות.
- **המקודדים zstd ו־⁦fast-lzma2⁩ משתמשים בסנכרון שזמין רק מ־Windows Vista ואילך.** שניהם כופים `_WIN32_WINNT 0x0600` בקובצי הכותרת (headers) שלהם וקוראים ישירות ל־`InitializeConditionVariable` / `SleepConditionVariableCS`, ולכן `7z.dll` ו־`7za.exe` – שני הקבצים הבינאריים שהמקודדים מהודרים בתוכם – מייבאים ארבע פונקציות שאינן קיימות ב־Windows XP וב־⁦Windows Server 2003.⁩ ה־`7z.dll` של המקור (upstream) אינו מייבא אף אחת מהן.
- שרשרת הכלים: הקבצים נבנים ב־⁦Visual Studio 2022⁩, שרשימת יעדי התמיכה שלו היא ⁦Windows 7⁩ ואילך – Vista ו־⁦Server 2008⁩ מסומנים “No” ([Microsoft](https://learn.microsoft.com/en-us/visualstudio/releases/2022/compatibility)). גרסת תת־המערכת (subsystem) המקושרת היא ⁦6.0⁩ ב־⁦x64⁩ וב־⁦x86⁩ ו־⁦6.2⁩ ב־⁦arm64⁩, ו־Windows ב־⁦arm64⁩ מתחיל ב־⁦Windows 10⁩ בכל מקרה.

המערכות Windows Vista ו־⁦Windows Server 2008⁩ נמצאות בתווך: הקבצים הבינאריים היו נטענים, אבל שרשרת הכלים אינה תומכת בהן, תוכנית ההתקנה לא תפעל שם, ו־⁦7-ZSTar⁩ לא נבדק עליהן.

**מערכת Linux נתמכת רק כבנייה בשורת פקודה; macOS אינה נתמכת.**
ה־fork בונה `7zz` נייטיב (native, תוכנית המסוף `Alone2`) באמצעות gcc, דרך makefile משלו שכולל את ה־makefile של המקור (upstream) ואינו משנה אף אחד מהם: `cd CPP/7zip/Bundles/Alone2 && make -j"$(nproc)" -f makefile.7zstar.gcc`.
הוא נבנה ונבדק רק ב־⁦Ubuntu 24.04⁩ עם ⁦gcc 13.3⁩ (⁦x86-64⁩): הבנייה נקייה מאזהרות תחת הדגלים של המקור, בדיקת העשן (smoke test) בת ⁦77⁩ הבדיקות עוברת, ו־⁦25⁩ וקטורי יכולת הפעולה ההדדית (interop) שנוצרו ב־Windows ו־⁦37⁩ שנוצרו ב־Linux נותנים אותם פסקי דין כמו ב־⁦Windows.⁩ שני הקבצים שבבעלות ה־fork שהפורט נגע בהם עדיין נבנים ללא שינוי ב־Windows (בנייה נקייה של ⁦x64⁩, בדיקות עשן וקריאה חוזרת של interop עוברות כולן). אין ממשק גרפי. יעדי Linux האחרים של המקור (`7za`, `7zr`, `7z.so`) אינם נתמכים: רשימות קובצי האובייקט שלהם ב־gcc חסרות את מה ששינויי ה־fork במטפלים של המקור דורשים, ולכן צפוי שהקישור שלהם ייכשל. ארכיטקטורות, הפצות ומהדרים אחרים לא אומתו, ו־macOS מעולם לא נבנה, ולכן אי אפשר לציין `MACOSX_DEPLOYMENT_TARGET`. שלבי הבנייה, הבדיקות והמגבלות הידועות נמצאים ב־`build/linux/README.md`; יכולת הפעולה ההדדית עם כלים של Linux מפורטת ב־`test/interop/REPORT.md`.

## חבילות לא חתומות, SmartScreen ובקרת אפליקציות חכמה

**תוכניות ההתקנה והתוכנות בגרסה של ⁦7-ZSTar⁩ אינן חתומות דיגיטלית על ידי רשות אישורים**, ולפרויקט הזה אין תעודת חתימת קוד. לכן Windows אינו יכול לדעת מי פרסם את הקובץ, וכשמפעילים את ה־`.msi`, או תוכנה מתוך ה־`.zip`, בפעם הראשונה, Microsoft Defender SmartScreen עלול לעצור אותם באזהרה. התיעוד למפתחים של Microsoft מונה “No signature” כאחד המקרים שבהם מוצגת אזהרה בשם “Windows protected your PC” (בעברית: “Windows הגן על המחשב שלך”), ושבהם על המשתמש לבחור “Run anyway” (בעברית: “הפעל בכל מקרה”) לפני שהאפליקציה תפעל ([Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). מדיניות ארגונית יכולה להסיר את האפשרות הזו לחלוטין; במחשב כזה יש לפנות למי שמנהל אותו.

הדבר היחיד בגרסה ש*כן* חתום הוא החבילה הקטנה שמציבה את ⁦7-ZSTar⁩ ברמה הראשונה של תפריט הלחיצה הימנית ב־⁦Windows 11⁩, בתוך ה־`.msi` לכל המשתמשים. התעודה שלה חתומה עצמית ונוצרת בעת בניית אותה חבילה בלבד, ולכן היא אינה חתימה של רשות אישורים ואינה אומרת דבר על מי בנה את החבילה; ראו [תפריט לחיצה ימנית ב־⁦Windows 11⁩](#תפריט-לחיצה-ימנית-בwindows-11) להסבר מה היא עושה ואיך לסרב לה.

האזהרה אינה הוכחה לכך שהקובץ פגום, והיעדרה לא יוכיח שהקובץ תקין. מה שאפשר לבדוק בעצמכם הוא שהעותק שלכם זהה בדיוק לזה שפורסם בדף הגרסה. כל גרסה כוללת קובץ בשם `SHA256SUMS`: שורה אחת לכל חבילה, גיבוב (hash) ⁦SHA-256⁩ ואחריו שם הקובץ.

1. הורידו את החבילה ואת `SHA256SUMS` מאותו דף גרסה, לאותה תיקייה.
2. פתחו PowerShell באותה תיקייה והשוו. החליפו את השם בשם הקובץ שהורדתם:

   ```powershell
   $name = '7-ZSTar-26.05.1-x64.msi'
   $expected = ((Get-Content .\SHA256SUMS | Where-Object { $_ -match ([regex]::Escape($name) + '$') }) -split '\s+')[0]
   $actual   = (Get-FileHash -Algorithm SHA256 -LiteralPath $name).Hash
   $actual -eq $expected
   ```

   הערך `True` פירושו שהגיבובים זהים. כדי לעיין בהם בעצמכם, הריצו `Get-FileHash -Algorithm SHA256 .\7-ZSTar-26.05.1-x64.msi` ומצאו את אותו שם קובץ ב־`SHA256SUMS`; ההשוואה אינה מבחינה בין אותיות גדולות לקטנות.
3. אם קיבלתם `False`, או ששם הקובץ אינו מופיע ב־`SHA256SUMS`, אל תפעילו אותו: מחקו את הקובץ והורידו אותו שוב. אם הוא עדיין אינו תואם, נא לדווח על כך כמתואר ב־[⁦SECURITY.md⁩](../../SECURITY.md).

הקובץ `SHA256SUMS` מכסה רק את הקבצים שהועלו לאותה גרסה. בנייה עצמית של אותו תג (tag) נותנת גיבובים שונים (חבילת תפריט הלחיצה הימנית נחתמת בתעודה חדשה בכל בנייה), וקוד המקור מתפרסם עם כל גרסה אם אתם מעדיפים לבנות בעצמכם: ראו [⁦build/README.md⁩](../../build/README.md).

אחרי שהגיבובים תואמים ואתם שבעי רצון מהמקור שממנו הגיע הקובץ:

- ‏**`.msi`** – הפעילו אותו כרגיל. אם SmartScreen עוצר אותו, בחרו באפשרות להפעיל אותו בכל זאת (“הפעל בכל מקרה” ב־Windows בעברית; “Run anyway” ב־Windows באנגלית). ייתכן שצריך קודם להרחיב את חלון האזהרה: במחשב ה־⁦Windows 10⁩ שנבדק הוא הציע רק את הכפתור “אל תפעיל” עד שנלחץ הקישור “מידע נוסף” שמתחת להודעה. אחרי כן ה־`.msi` לכל המשתמשים מבקש אישור של מנהל מערכת כמו כל תוכנית התקנה אחרת.
- ‏**`.zip`** – חלצו אותו והפעילו את `7zFM.exe` או את `7z.exe` מתוך התיקייה. גם התוכנות שבפנים אינן חתומות, ולכן Windows עשוי להציג את אותה אזהרה בפעם הראשונה שמפעילים כל אחת מהן.

‏SmartScreen מזהיר לפי מידת ההיכרות עם הקובץ ולא רק לפי חתימות; קובץ שהורידו אותו מעט אנשים יכול להפעיל את האזהרה גם כשהוא חתום. שום דבר כאן אינו משנה זאת, ושום דבר בשלבים שלמעלה אינו מכבה את ⁦SmartScreen.⁩

### בקרת אפליקציות חכמה ב־Windows 11

בחלק ממחשבי ⁦Windows 11⁩ מופעלת הגנה מחמירה יותר בשם **בקרת אפליקציות חכמה** (Smart App Control). כשהיא מופעלת, Windows חוסם קבצים לא חתומים אלא אם שירות הענן של Microsoft יכול לערוב להם, ולגרסה חדשה בדרך כלל אין רישום כזה ([Microsoft](https://support.microsoft.com/en-us/windows/smart-app-control-frequently-asked-questions-285ea03d-fa88-4d56-882e-6698afdb7003), [Microsoft](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). בניגוד לאזהרת SmartScreen, בחסימה אין אפשרות להפעיל את הקובץ בכל זאת, וב־FAQ של Microsoft נאמר שאין דרך לעקוף את בקרת האפליקציות החכמה עבור אפליקציה בודדת.

מה קרה כשניסו את ⁦7-ZSTar 26.05.1⁩ ב־⁦Windows 11 Pro 25H2⁩ (⁦build 26200.8037⁩) כשבקרת האפליקציות החכמה מופעלת:

- **תוכניות ההתקנה מסוג `.msi` נחסמו**, גם זו לכל המשתמשים וגם זו למשתמש יחיד. ב־Windows בסינית מסורתית, Windows Installer הציג 「系統禁用此安裝。請連絡系統管理員。」 (בערך: המערכת אוסרת את ההתקנה הזו, נא לפנות למנהל המערכת), והודעה של אבטחת Windows ציינה שבקרת האפליקציות החכמה חסמה את הקובץ כי Windows לא הצליח לדעת מי פרסם אותו והוא אינו אפליקציה ש־Windows מכיר. לא הייתה אפשרות להמשיך, ו־`msiexec /i ... /qn` החזיר שגיאה ⁦1625.⁩ ההודעה הזו היא מחרוזת ⁦1625⁩ של Windows Installer; ב־Windows באנגלית אותה מחרוזת היא “⁦The system administrator has set policies to prevent this installation.⁩” (נקראה ממשאבי האנגלית של Windows Installer, לא נראתה על המסך).
- **תוכנה מתוך ה־`.zip` פעלה.** `7zFM.exe`, שחולץ מה־`.zip` הנייד, התחיל לפעול כרגיל באותה בדיקה. השאלה אם Windows מתיר להריץ תוכנה לא חתומה היא שיקול דעת של Windows לגבי אותו קובץ, ולכן ייתכן שאצלכם התוצאה שונה.
- מיד אחרי שבקרת האפליקציות החכמה הופעלה, ה־`.msi` הותקן במשך כמה דקות לפני שהחל להיחסם. הסיבה לא נמצאה, ולכן הצלחה מיד אחרי ההפעלה אינה אומרת שתוכנית ההתקנה מותרת.

לכן במחשב שבו בקרת האפליקציות החכמה מופעלת, **אי אפשר להתקין את תוכניות ההתקנה**, ובדיקת `SHA256SUMS` אינה משנה זאת. מה שכן משנה זאת הוא כיבוי בקרת האפליקציות החכמה ב־הגדרות בקרת אפליקציות חכמה של אפליקציית אבטחת Windows (ב־Windows בסינית מסורתית שנבדק: Windows 安全性, 應用程式與瀏覽器控制, 智慧型應用程式控制設定). בבדיקה, בחירה באפשרות “כבוי” נכנסה לתוקף מיד, בלי הפעלה מחדש, ואז תוכניות ההתקנה הותקנו. זו הגדרה של המחשב כולו ושום דבר כאן אינו מבקש ממכם לשנות אותה: ההחלטה בידיכם, או בידי מנהל המערכת שלכם במחשב מנוהל.

כדאי לדעת מראש גם אם אפשר להפעיל אותה מחדש. ב־FAQ של Microsoft נאמר שעדכוני Windows אחרונים מאפשרים להפעיל את בקרת האפליקציות החכמה שוב בלי התקנה נקייה של Windows, ולכן בגרסה בלעדיהם כיבוי עלול להיות קבוע. בגרסה שנבדקה כאן האפשרות להפעיל אותה עדיין הוצעה אחרי הכיבוי; זו תוצאת בדיקה ולא הבטחה לגבי הגרסה שלכם.

## התקנה

שלוש חבילות, וכולן נבנות על ידי `installer\Build-Package.ps1` (זו שלמשתמש יחיד – עם `-PerUser`):

| | `.msi` | `-user.msi` | `.zip` |
|---|---|---|---|
| מותקנת עבור | כל החשבונות | החשבון שמתקין | - |
| תפריט לחיצה ימנית בסייר הקבצים | כן | כן, התפריט הקלאסי בלבד ([להלן](#החבילה-ברמת-המשתמש)) | לא |
| פריט בתפריט התחלה | כן | כן | לא |
| דורשת מנהל מערכת | כן | לא | לא |
| הסרה | *אפליקציות מותקנות* בהגדרות | *אפליקציות מותקנות* בהגדרות | מחיקת התיקייה |

*אפליקציות מותקנות* הוא השם ב־⁦Windows 11.⁩ ב־⁦Windows 10⁩ אותו דף נקרא *אפליקציות ותכונות*, וב־⁦Windows 7⁩ זה *Programs and Features* (תוכניות ותכונות) ב־Control Panel (לוח הבקרה).

השתמשו בחבילות שמתאימות ל־Windows עצמו: ⁦x86⁩ ב־Windows של ⁦32⁩ סיביות, ⁦x64⁩ ב־Windows של ⁦64⁩ סיביות, ⁦arm64⁩ ב־Windows ל־Arm (חבילות ה־⁦arm64⁩ נבנות אך מעולם לא הורצו). הרחבת המעטפת (shell extension) של ⁦x86⁩ היא של ⁦32⁩ סיביות וסייר הקבצים של ⁦64⁩ סיביות אינו יכול לטעון אותה, ולכן ב־Windows של ⁦64⁩ סיביות ל־`-user.msi` של ⁦x86⁩ אין תפריט לחיצה ימנית בכלל, ול־`.msi` של ⁦x86⁩ יש כזה רק ב־⁦Windows 11⁩ ורק בחשבונות שרשמו את חבילת ה־⁦Windows 11⁩ שלו (החשבון שהתקין, או חשבון שהריץ `-Register`, להלן).

ה־MSI מתקין אל `Program Files\7-ZSTar` – תמיד: בניגוד לחבילה ברמת המשתמש הוא אינו מציע בחירת תיקייה, ומתעלם מ־`INSTALLFOLDER` בשורת הפקודה, כי בתיקייה הזו נמצא סקריפט שתוכנית ההתקנה מריצה בתור SYSTEM ו־DLL שסייר הקבצים של כל משתמש טוען, ותיקייה שנוצרה במקום אחר (למשל תחת `C:\`) ניתנת לכתיבה לכל משתמש. הוא רושם CLSID משלו להרחבת המעטפת וענף רישום (registry) משלו, `Software\7-ZSTar`, וקורא לכל מפתח של תפריט ההקשר `7-ZSTar` – כך שאינו מתנגש עם זה של ⁦7-Zip⁩ הרשמי ואינו מסיר אותו. ראו [⁦installer/GUIDS.md⁩](../../installer/GUIDS.md).

הוא מריץ אשף התקנה רגיל – welcome, licence, setup type, optional feature tree, finish (ברוכים הבאים, רישיון, סוג ההתקנה, עץ התכונות האופציונליות, סיום) – וההתקנה השקטה עדיין פועלת ללא שינוי (`msiexec /i 7-ZSTar-<version>-<arch>.msi /qn`), כי msiexec מדלג על כל רצף הממשק במצב שקט. האשף באנגלית בלבד, גם ב־Windows שמוגדר לשפה אחרת (נראה ב־⁦Windows 10⁩ בסינית מסורתית; ה־`.msi` נבנה בלי שפה אחרת), ובעמוד הסיום שלו האפשרות *⁦Launch 7-ZSTar File Manager⁩* מסומנת כברירת מחדל.

### תפריט לחיצה ימנית ב־Windows 11

ב־⁦Windows 11⁩ הפריט נמצא בתפריט ברמה הראשונה, ולא קבור תחת *הצג אפשרויות נוספות*, שם עדיין יושבים ⁦7-Zip⁩ הרשמי ו־⁦WinRAR. Windows 11⁩ מציג שם הרחבת מעטפת רק כשיש לה זהות חבילה (package identity), ולכן ה־MSI מספק חבילת MSIX קטנה שכל תפקידה זהות, לצד התוכנה, ורושם אותה במהלך ההתקנה. הרישום הקלאסי נשמר גם הוא. הוא זה שמציב את הפריט בתפריט הלחיצה הימנית ב־⁦Windows 10⁩ וב־⁦Windows 7⁩, שהתפריט שלהם בעל רמה אחת, בלי *הצג אפשרויות נוספות*, והוא זה שממשיך לעבוד אצל מי ששחזר את תפריט ההקשר הישן.

החבילה הזו חתומה בתעודה **חתומה עצמית**, ותוכנית ההתקנה מכניסה אותה אל `LocalMachine\TrustedPeople` – Windows לא יפרוס חבילה שאת חתימתה הוא אינו יכול לשרשר למשהו מהימן. ההסרה מסירה את התעודה יחד עם החבילה. ב־⁦Windows 10⁩ וב־⁦Windows 7⁩ תוכנית ההתקנה אינה עושה אף אחד משני הדברים: היא אינה מוסיפה תעודה ואינה רושמת חבילה, והרישום הקלאסי לבדו מספק את התפריט.

אם אתם מעדיפים שלא לתת אמון בתעודה חתומה עצמית, אפשר לסרב רק לחלק הזה ולהשאיר את כל השאר:

```
msiexec /i 7-ZSTar-<version>-<arch>.msi SPARSE=0
```

אז מקבלים רק את התפריט הקלאסי, ולכן ב־⁦Windows 11⁩ הפריט של ⁦7-ZSTar⁩ נמצא בתפריט הלחיצה הימנית תחת *הצג אפשרויות נוספות*. כדי להפעיל מאוחר יותר את הפריט ברמה הראשונה, או לבטל אותו אחרי התקנה רגילה:

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -TrustCert -Register
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -Unregister -UntrustCert
```

מתן אמון בתעודה הזו פירושו ש־Windows יקבל גם **כל חבילה אחרת** שנחתמה באותו מפתח, בלי אזהרה. היא משמשת רק לחבילה האחת הזו, וההסרה מוציאה אותה בחזרה, אבל זה מה שאתם מסכימים לו – `SPARSE=0` שלמעלה הוא הדרך לסרב לכך.

רישום החבילה הוא לפי משתמש, ותוכנית ההתקנה מריצה אותו רק עבור מי שהתקין. שתי השלכות:

- חשבון שני באותו מחשב מקבל רק את התפריט הקלאסי, עד שהוא מריץ את אותו סקריפט עם `-Register`.
- ההסרה מבטלת את הרישום רק עבור מי שמסיר. אם מישהו אחר רשם אותה, הרישום שלו שורד את ההסרה ומצביע על תיקייה שכבר אינה קיימת; אותו חשבון מנקה אותו באמצעות `Get-AppxPackage 7-ZSTar | Remove-AppxPackage`.

**מגבלה ידועה: התפריט ברמה הראשונה נרשם רק כשההתקנה רצה בסשן אינטראקטיבי שבו המשתמש מחובר.** התקנת ה־`.msi` לכל המשתמשים מסשן מרוחק או לא אינטראקטיבי – דרך SSH, או פריסה שקטה מכלי ניהול – עדיין מדווחת על הצלחה, אבל חבילת ⁦Windows 11⁩ אינה נרשמת, ולכן מופיע רק התפריט הקלאסי תחת *הצג אפשרויות נוספות*. בבדיקה, `msiexec /i ... /qn` מסשן SSH (סשן ⁦0⁩) יצא עם ⁦0⁩ ואילו `Setup-ShellIntegration.ps1` דיווח `registration failed: 0x80070005` (⁦Access is denied.⁩ – גישה נדחתה); אותו `.msi` שהותקן מסשן הקונסולה של מנהל מערכת נרשם כרגיל.

הפרמטר `-Status` מדפיס מה קיים ומה אינו קיים.

### החבילה ברמת המשתמש

הקובץ `7-ZSTar-<version>-<arch>-user.msi` מותקן עבור החשבון הנוכחי בלבד, אל `%LOCALAPPDATA%\Programs\7-ZSTar`, בלי חלון של בקרת חשבון משתמש (UAC). כל מה שהוא רושם נכנס תחת `HKCU`; החבילה אינה כותבת דבר אל `HKLM` (מלבד הרישום הפנימי של Windows Installer עצמו). מה שהיא אינה עושה כמו החבילה ברמת המחשב:

- **אין תפריט ברמה הראשונה ב־⁦Windows 11⁩.** ב־⁦Windows 11⁩, ⁦7-ZSTar⁩ נמצא בתפריט הלחיצה הימנית תחת *הצג אפשרויות נוספות*. הפריט ברמה הראשונה דורש שהתעודה החתומה עצמית תהיה מהימנה ברמת המחשב כולו, מה שדורש מנהל מערכת: נמדד ב־⁦Windows 11⁩ שתעודה ב־`CurrentUser\TrustedPeople` אינה מספיקה כדי ש־Windows יפרוס את החבילה. לכן החבילה ברמת המשתמש משמיטה אותו.
- **רק אחת משתיים במחשב.** כל חבילה מסרבת להתקין כשהאחרת מותקנת; הסירו אחת לפני שמתקינים את השנייה. החבילה ברמת המחשב רואה רק את העותק ברמת המשתמש של החשבון שמריץ אותה, ולכן התקנה ברמת המשתמש של חשבון אחר אינה מזוהה.
- **מדיניות קבוצתית יכולה להסתיר את התפריט שלה.** במקום שבו מוגדר `EnforceShellExtensionSecurity`, סייר הקבצים טוען רק הרחבות מעטפת שמופיעות תחת המפתח *Approved* ברמת המחשב, שהתקנה ברמת המשתמש אינה יכולה לכתוב אליו, ולכן תפריט הלחיצה הימנית אינו מופיע. השתמשו שם בחבילה ברמת המחשב.
- **ניקוי פורמט תחת כלים > …אפשרויות > מערכת מסיר גם את ההצעה של ⁦7-ZSTar⁩ לפורמט הזה.** כשמנקים שם פורמט (לוחצים על התא שלו עד שהוא ריק, ואז על אשר), מנהל הקבצים מוחק את המפתחות `HKCU\Software\Classes\.<ext>` ו־`7-ZSTar.<ext>` בשלמותם – ובהתקנה ברמת המשתמש המפתחות האלה מחזיקים גם את מה שהחבילה רשמה עבור הגדרות > אפליקציות > אפליקציות המוגדרות כברירת מחדל ועבור הרשימה *פתח באמצעות*. אז ⁦7-ZSTar⁩ נעלם מהרשימה *פתח באמצעות* של אותו פורמט, ובדף אפליקציות המוגדרות כברירת מחדל מוצג עבורו פריט ריק. תיקון ההתקנה מחזיר אותו (הפעילו שוב את ה־`.msi` ובחרו *Repair*). עדיף לשייך סוגי קבצים בדף אפליקציות המוגדרות כברירת מחדל ולא במנהל הקבצים. לחבילה ברמת המחשב יש אותה נקודת תורפה במקום אחד, שמתואר להלן בפרק שיוכי הקבצים.

### שיוכי קבצים, ומה ההסרה עושה להם

**הגדירו אותם בהגדרות > אפליקציות > אפליקציות המוגדרות כברירת מחדל.** ב־⁦Windows 11⁩ מקלידים שם ⁦7-ZSTar⁩ וכל פורמט שהוא יכול לפתוח מופיע ברשימה לשיוך. ב־⁦Windows 10⁩, ⁦7-ZSTar⁩ מופיע בדף הזה תחת *Set defaults by app* (קביעת ברירות מחדל לפי אפליקציה), ושם *Manage* (ניהול) מציג את הפורמטים שלו. ל־⁦Windows 7⁩ אין אפליקציית הגדרות: ⁦7-ZSTar⁩ מופיע תחת Control Panel > תוכניות ברירת מחדל > *קבע את תוכניות ברירת המחדל שלך*, וזה מה שמסומן במדריך הזה כ״אפליקציות המוגדרות כברירת מחדל״ שם. שיוך פורמטים משני הדפים האלה לא נבדק. תוכנית ההתקנה רושמת את ⁦7-ZSTar⁩ כאפליקציית תוכניות ברירת מחדל – ProgID לכל פורמט עם הסמל ופקודת הפתיחה שלו, פריט ברשימה *פתח באמצעות* של כל סיומת, ובלוק ה־Capabilities ש־Windows קורא – אבל היא במכוון אינה תובעת שום סוג קובץ: איזו תוכנה פותחת את הארכיונים שלכם היא החלטה שלכם, וזה מה ששומר ש־⁦7-ZSTar⁩ ו־⁦7-Zip⁩ הרשמי לא יפריעו זה לזה. Windows עדיין יכול לשלוח פורמט אל ⁦7-ZSTar⁩ מעצמו כשאף תוכנה אחרת אינה מציעה לפתוח אותו: במחשבי ה־⁦Windows 10⁩ וה־⁦Windows 7⁩ שנבדקו, שבהם דבר אחר לא רשם את `.7z`, קובץ `.7z` הציג את הסמל של ⁦7-ZSTar⁩ ונפתח בו בלחיצה כפולה, בלי ש־Windows ישאל באיזו תוכנה להשתמש.

**כלים > …אפשרויות > מערכת במנהל הקבצים ברובו אינו עובד ב־⁦Windows 11⁩**, וזה כלל של Windows ולא באג כאן. הוא כותב ProgID בשם `7-ZSTar.<ext>` אל `HKCU\Software\Classes`, ועבור כל סיומת שהמחשב כבר מכיר – וכל פורמט ארכיון כזה – ⁦Windows 11⁩ מתעלם ממנו: `AssocQueryString` עונה `Unknown` וסייר הקבצים מצייר את הסמל הגנרי הריק. מה שהוא מכבד במקום זאת הוא מפתח `UserChoice` שחתום בגיבוב ש־Windows בלבד יכול לחשב, ולכן ממשק ההגדרות הוא הדרך היחידה שם. שום אפליקציה אינה יכולה לכתוב אחד כזה: לא ⁦7-ZSTar⁩, לא ⁦7-Zip⁩, ולא תוכנית התקנה כלשהי. ב־⁦Windows 10⁩ וב־⁦Windows 7⁩ ההתנהגות הייתה שונה בבדיקה: אחרי שהוגדרו `.7z` ו־`.zst` במנהל הקבצים, בלי שנבחרה עבורם תוכנה אחרת, `AssocQueryString` החזיר `7zFM.exe` עבור שניהם.

**ניקוי פורמט בעמודה *כל המשתמשים* מסיר את הרישום של החבילה ברמת המחשב עבורו.** העמודה הזו כותבת אל `HKLM\Software\Classes`, שם החבילה ברמת המחשב מחזיקה את ה־ProgID ואת הפריטים של *פתח באמצעות* שהיא מפרסמת, וניקוי פורמט שם (מה שדורש להפעיל את מנהל הקבצים באמצעות “הפעל כמנהל מערכת”) מוחק את המפתחות האלה בשלמותם – עבור כל החשבונות. תיקון ההתקנה החזיר את אותם מפתחות עבור החבילה ברמת המשתמש; עבור זו לא נמדד.

**סמל שנשאר ריק אחרי שינוי כלשהו** עשוי להיות גם בגלל מטמון הסמלים של סייר הקבצים, שאינו מבחין שקובץ DLL שכבר נשמר בו הוחלף; `ie4uinit.exe -show` אינו מנקה אותו באופן מהימן. סגרו את סייר הקבצים, מחקו את `%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db`, והפעילו אותו שוב.

**ההסרה מסירה את השיוכים שהיא יכולה להגיע אליהם** – ה־ProgID בשם `7-ZSTar.*` ששייכים למי שמסיר, ורק את סוגי הקבצים שעדיין מצביעים אליהם, כך שפורמט שהועבר בינתיים לתוכנה אחרת נשאר כפי שהוא. הסרת החבילה ברמת המחשב גם משאירה ProgID שפותח עותק של ⁦7-ZSTar⁩ במקום אחר שעדיין קיים – עותק נייד מה־`.zip`, שהוגדר באמצעות **כלים > …אפשרויות > מערכת** של אותו עותק. החבילה ברמת המשתמש אינה יכולה לעשות זאת: ה־ProgID שלה הם אותם מפתחות `HKCU` (ראו *החבילה ברמת המשתמש* לעיל), וההסרה מסירה אותם בלי קשר למי שכתב אותם אחרון. השארתם הייתה מפנה את סוגי הקבצים האלה אל ProgID שהסמל והפקודה שלו הם קובץ הפעלה שנמחק, כלומר סמל ריק ושגיאה בלחיצה כפולה. השיוכים של חשבונות אחרים מחוץ להישג יד; הם יכולים לנקות את שלהם באמצעות `Setup-ShellIntegration.ps1 -RemoveAssociations` לפני שהתוכנה מוסרת. `msiexec /x ... KEEPASSOC=1` מדלג על כך, ושדרוג אינו עושה זאת לעולם.

**מגבלה ידועה: חשבונות אחרים שומרים את השיוכים שהגדירו בעצמם.** הסרת החבילה ברמת המחשב מנקה רק את מה שהחשבון המריץ את ההסרה הגדיר בעמודה שלו (עם שם החשבון ככותרת) תחת **כלים > …אפשרויות > מערכת** במנהל הקבצים. כל חשבון אחר שהגדיר שם שיוכים שומר אותם, והם מצביעים על התוכנה שהוסרה, ולכן לחיצה כפולה על קובץ `.7z` גורמת ל־Windows לשאול באיזו תוכנה להשתמש. כל חשבון צריך לנקות את שלו **לפני** ההסרה, באמצעות

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -RemoveAssociations
```

ניקוי ההסרה אינו נוגע כלל בשיוכים שהוגדרו בעמודה **כל המשתמשים**, והם נשארים כשהם מפנים כל חשבון אל התוכנה שהוסרה. מנהל מערכת שהגדיר כאלה צריך לנקות את התאים האלה, ממנהל קבצים שהופעל באמצעות “הפעל כמנהל מערכת”, ואז אשר, לפני ההסרה; `-RemoveAssociations` אינו מגיע לעמודה הזו. ניקוי שלה ממש לפני הסרה אינו מזיק, אף שהוא מוחק שם את הרישום של החבילה עצמה (לעיל), כי ההסרה מסירה אותו בכל מקרה. לחבילה ברמת המשתמש אין את בעיית החשבונות האחרים, ו־⁦7-Zip⁩ הרשמי מתנהג כך גם הוא.
