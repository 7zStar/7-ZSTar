## システム要件

**Windows 7またはWindows Server 2008 R2、x64またはx86。arm64ではWindows 10。**
ほかに必要なものはありません。Cランタイムは静的にリンクされている（`-MT`）ため、バイナリが読み込むのはWindows自身のDLLだけで、再頒布可能パッケージも.NETも要りません。

この下限は、パッケージが必要とするものから*導き出したもの*で、後続の更新プログラムを適用したWindows 7 SP1（PowerShell 5.1を含む）、Windows 10 22H2、Windows 11（いずれも64ビット）で動作を確認しています。Windows 7と10では、すべてのユーザー向けおよびユーザー単位のx64 `.msi`のインストールとアンインストール、インストール ウィザード、x64 `.zip`、追加したすべてのコーデックと一度で処理できるtar形式、右クリックメニュー、ファイルの関連付け、ヘルプファイルを確認し、さらに64ビット版Windows上でx86の`.msi`と`.zip`が動くことも確認しました。それ以外はWindowsでは確認していません。Windows 8や8.1、Windows Server、32ビット版Windows、arm64のハードウェア、そしてそれらの更新プログラムがないWindows 7も、確認していません。この下限は、バイナリが今もWindows XPで読み込める上流の7-Zipより高くなっています。理由は3つあり、2つ目は、どのビルド設定でも覆せないものです。

- `.msi`は`InstallerVersion="500"`を宣言しており、Windows インストーラー 5.0は"with Windows Server 2008 R2 and later and Windows 7 and later"（Windows Server 2008 R2以降およびWindows 7以降に付属）として提供されました（[Microsoft][msi-versions]）。ポータブルな`.zip`はWindows インストーラーを通りませんが、次の2項目を参照してください。
- **zstdとfast-lzma2は、Vista以降にしかない同期機能を使います**。どちらも自分のヘッダーで`_WIN32_WINNT 0x0600`を強制し、`InitializeConditionVariable` / `SleepConditionVariableCS`を直接呼び出します。そのため、コーデックを組み込んだ2つのバイナリである`7z.dll`と`7za.exe`は、Windows XPとServer 2003にない4つの関数をインポートします。上流の`7z.dll`はそれらを1つもインポートしません。
- ツールチェーン：これらはVisual Studio 2022でビルドしており、サポートされるターゲットはWindows 7以降です。VistaとServer 2008は"No"です（[Microsoft][vs-targeting]）。リンクされるサブシステムのバージョンはx64とx86で6.0、arm64で6.2で、arm64版のWindowsはいずれにせよWindows 10から始まります。

Windows VistaとServer 2008は、その中間にあたります。バイナリは読み込めるはずですが、ツールチェーンがサポートしておらず、インストーラーはそこでは動かず、7-ZSTarもそれらでテストしていません。

**Linuxはコマンドラインでのビルドのみ対応しており、macOSには対応していません。**
このフォークは、gccと独自のmakefileで、ネイティブの`7zz`（`Alone2`コンソール プログラム）をビルドします。このmakefileは上流のmakefileをincludeするだけで、上流のものは1つも変更しません。
`cd CPP/7zip/Bundles/Alone2 && make -j"$(nproc)" -f makefile.7zstar.gcc`
ビルドとテストを行ったのはUbuntu 24.04とgcc 13.3（x86-64）だけです。上流のフラグでビルドして警告は出ず、77項目のスモーク テストに合格し、Windowsで作成した25個とLinuxで作成した37個の相互運用ベクターは、Windowsと同じ判定になります。移植で触れたフォーク側の2つのファイルは、Windowsでも変更なしでビルドできます（x64のクリーン ビルド、スモーク テスト、相互運用の読み戻しがすべて合格）。GUIはありません。上流のほかのLinuxターゲット（`7za`、`7zr`、`7z.so`）には対応していません。それらのgccオブジェクト リストには、上流のハンドラーに対するフォークの変更が必要とするものが含まれていないため、リンクに失敗すると見込まれます。ほかのアーキテクチャ、ディストリビューション、コンパイラーは検証しておらず、macOSは一度もビルドしたことがないため、`MACOSX_DEPLOYMENT_TARGET`を示すことはできません。ビルド手順、テスト、既知の制限は`build/linux/README.md`に、Linuxツールとの相互運用性は`test/interop/REPORT.md`にあります。

## 未署名のパッケージ、SmartScreen、スマート アプリ コントロール

**7-ZSTarのリリースに含まれるインストーラーとプログラムは、認証局によるコード署名がされていません**。このプロジェクトはコード署名証明書も持っていません。そのためWindowsは、ファイルの発行元を判別できず、`.msi`、または`.zip`内のプログラムを初めて実行するときに、Microsoft Defender SmartScreenが警告を表示して止めることがあります。Microsoftの開発者向けドキュメントは、"No signature"（署名なし）を、「Windows によって PC が保護されました」という警告（ドキュメントの表記は"Windows protected your PC"）が表示されるケースの1つとして挙げています。その警告では、アプリが実行される前に、利用者が「実行」（ドキュメントの表記は"Run anyway"）を選ぶ必要があります（[Microsoft][smartscreen-rep]）。企業のポリシーでこの選択肢自体を削除することもできます。そのようなPCでは、管理している担当者に問い合わせてください。

リリースの中で*署名されている*唯一のものは、すべてのユーザー向けの`.msi`に入っている、7-ZSTarをWindows 11の右クリックメニューの第1階層に載せる小さなパッケージです。その証明書は自己署名で、そのパッケージだけをビルドするときに生成されるため、認証局の署名ではなく、誰がパッケージをビルドしたかについては何も保証しません。何をするものか、また断る方法は、[Windows 11の右クリックメニュー](#windows-11の右クリックメニュー)を参照してください。

警告は、ファイルが悪いことの証明ではなく、警告が出ないことも、ファイルが良いことの証明にはなりません。自分で確認できるのは、手元のコピーがリリース ページで公開されているものと完全に同じかどうかです。どのリリースにも`SHA256SUMS`というファイルが付いています。パッケージごとに1行で、SHA-256ハッシュのあとにファイル名が続きます。

1. パッケージと`SHA256SUMS`を、同じリリース ページから同じフォルダーにダウンロードします。
2. そのフォルダーでPowerShellを開き、比較します。名前は、ダウンロードしたファイルの名前に置き換えてください。

   ```powershell
   $name = '7-ZSTar-26.05.1-x64.msi'
   $expected = ((Get-Content .\SHA256SUMS | Where-Object { $_ -match ([regex]::Escape($name) + '$') }) -split '\s+')[0]
   $actual   = (Get-FileHash -Algorithm SHA256 -LiteralPath $name).Hash
   $actual -eq $expected
   ```

   `True`はハッシュが同じという意味です。自分の目で確かめたい場合は、代わりに`Get-FileHash -Algorithm SHA256 .\7-ZSTar-26.05.1-x64.msi`を実行し、同じファイル名を`SHA256SUMS`の中から探してください。比較では大文字と小文字は区別されません。
3. `False`になった場合や、ファイル名が`SHA256SUMS`にない場合は、実行しないでください。ファイルを削除して、もう一度ダウンロードします。それでも一致しない場合は、[SECURITY.md](../../SECURITY.md)に書かれているとおり報告してください。

`SHA256SUMS`は、そのリリースにアップロードされたファイルだけが対象です。同じタグを自分でビルドするとハッシュは変わります（右クリックメニューのパッケージは、ビルドのたびに新しい証明書で署名されるため）。ソースコードもリリースごとに公開しているので、自分でビルドすることもできます。[build/README.md](../../build/README.md)を参照してください。

ハッシュが一致し、ファイルの入手元にも納得できたら：

- **`.msi`**：通常どおり起動します。SmartScreenに止められたら、それでも実行するための選択肢を選びます（英語版Windowsでは"Run anyway"、日本語版Windowsでは「実行」）。警告ウィンドウは、最初に展開が必要な場合があります。テストしたWindows 10のマシンでは、メッセージの下のリンクをクリックするまで、ファイルを実行しないためのボタンしか表示されませんでした。そのあと、すべてのユーザー向けの`.msi`は、ほかのインストーラーと同じように管理者の承認を求めます。
- **`.zip`**：展開して、フォルダーの`7zFM.exe`または`7z.exe`を起動します。中のプログラムも署名されていないため、それぞれを最初に起動するときに、Windowsが同じ警告を表示することがあります。

SmartScreenはファイルの知名度に基づいて警告するもので、署名の有無だけが基準ではありません。ダウンロードした人が少ないファイルは、署名されていても警告の対象になることがあります。ここに書いたことでそれが変わるわけではなく、上の手順のどれもSmartScreenをオフにするものではありません。

### Windows 11のスマート アプリ コントロール

一部のWindows 11のPCでは、**スマート アプリ コントロール**というより厳格な保護がオンになっています。オンのとき、Windowsは、Microsoftのクラウド サービスが保証できない限り、署名のないファイルをブロックします。新しいリリースには、通常そのような記録がありません（[Microsoft][sac-faq]、[Microsoft][smartscreen-rep]）。SmartScreenの警告と違って、このブロックにはファイルをそれでも実行する選択肢がなく、MicrosoftのFAQにも、個々のアプリについてスマート アプリ コントロールを回避する方法はないと書かれています。

7-ZSTar 26.05.1を、スマート アプリ コントロールをオンにしたWindows 11 Pro 25H2（ビルド26200.8037）で試したときの結果：

- **`.msi`インストーラーはブロックされました**。すべてのユーザー向けも、ユーザー単位も同じです。繁体字中国語版のWindowsでは、Windows インストーラーが「系統禁用此安裝。請連絡系統管理員。」と表示し、Windows セキュリティの通知には、発行元をWindowsが判別できず、Windowsが把握しているアプリでもないため、スマート アプリ コントロールがファイルをブロックした、と表示されました。続行する選択肢はなく、`msiexec /i ... /qn`はエラー1625を返しました。このメッセージはWindows インストーラーの文字列1625です。英語版Windowsでは、同じ文字列が"The system administrator has set policies to prevent this installation."となります（Windows インストーラーの英語リソースから読み取ったもので、画面では確認していません）。
- **`.zip`のプログラムは実行できました。** ポータブル`.zip`から展開した`7zFM.exe`は、同じテストで普通に起動しました。署名のないプログラムの実行を許可するかどうかは、Windowsがそのファイルごとに下す判断なので、お使いのPCでは異なる可能性があります。
- スマート アプリ コントロールをオンにした直後は、`.msi`が数分間インストールでき、そのあとブロックされ始めました。原因は分かっていないため、オンにした直後にインストールできたからといって、インストーラーが許可されているとは限りません。

したがって、スマート アプリ コントロールがオンのPCでは、**インストーラーをインストールできません**。`SHA256SUMS`を確認しても、それは変わりません。変わるのは、Windows セキュリティ アプリのスマート アプリ コントロールの設定で、スマート アプリ コントロールをオフにすることです（テストした繁体字中国語版Windowsでは：Windows 安全性, 應用程式與瀏覽器控制, 智慧型應用程式控制設定）。テストでは、「オフ」のオプションを選ぶとすぐに有効になり、再起動は不要で、そのあとインストーラーをインストールできました。これはPC全体の設定で、ここで変更をお願いするものではありません。変更するかどうかは、あなた自身、または管理されているPCでは管理者が決めることです。

再びオンにできるかどうかも、先に知っておくとよいでしょう。MicrosoftのFAQには、最近のWindows更新プログラムでは、Windowsをクリーン インストールしなくてもスマート アプリ コントロールを再びオンにできる、とあります。したがって、それらがないバージョンでは、オフにすると元に戻せない可能性があります。ここでテストしたビルドでは、オフにしたあとも、オンにするオプションが表示されていました。これはテスト結果であり、お使いのバージョンについての保証ではありません。

[sac-faq]: https://support.microsoft.com/en-us/windows/smart-app-control-frequently-asked-questions-285ea03d-fa88-4d56-882e-6698afdb7003

## インストール

3種類のパッケージがあり、すべて`installer\Build-Package.ps1`でビルドします（ユーザー単位のものは`-PerUser`付き）。

| | `.msi` | `-user.msi` | `.zip` |
|---|---|---|---|
| インストール対象 | すべてのアカウント | インストールを行ったアカウント | - |
| エクスプローラーの右クリックメニュー | あり | あり（従来のメニューのみ。[後述](#ユーザー単位のパッケージ)） | なし |
| スタート メニューのエントリ | あり | あり | なし |
| 管理者権限が必要 | はい | いいえ | いいえ |
| 削除 | 設定の*インストールされているアプリ* | 設定の*インストールされているアプリ* | フォルダーを削除 |

*インストールされているアプリ*はWindows 11での名前です。Windows 10では同じページを*アプリと機能*と呼び、Windows 7ではコントロール パネルの*プログラムと機能*にあたります。

お使いのWindowsに合ったパッケージを使ってください。32ビット版Windowsにはx86、64ビット版Windowsにはx64、Windows on Armにはarm64です（arm64パッケージはビルドされていますが、一度も実行したことはありません）。x86のシェル拡張は32ビットで、64ビット版のエクスプローラーは読み込めません。そのため、64ビット版Windowsではx86の`-user.msi`には右クリックメニューがまったくなく、x86の`.msi`のメニューはWindows 11でのみ、しかもそのWindows 11用パッケージを登録したアカウント（インストールしたアカウント、または後述の`-Register`を実行したアカウント）にだけ表示されます。

MSIは常に`Program Files\7-ZSTar`にインストールされます。ユーザー単位のパッケージと違ってフォルダーを選ぶことはできず、コマンドラインの`INSTALLFOLDER`も無視します。そのフォルダーには、インストーラーがSYSTEMとして実行するスクリプトと、すべてのユーザーのエクスプローラーが読み込むDLLが置かれるため、ほかの場所（たとえば`C:\`の直下）に作ったフォルダーは、すべてのユーザーが書き込めてしまうからです。独自のシェル拡張のCLSIDと独自の`Software\7-ZSTar`レジストリ ハイブを登録し、コンテキストメニューのキーにはすべて`7-ZSTar`という名前を付けます。そのため、公式7-Zipのものと衝突することも、それを削除することもありません。[installer/GUIDS.md](../../installer/GUIDS.md)を参照してください。

通常のインストール ウィザード（welcome, licence, setup type, optional feature tree, finish：ようこそ、使用許諾契約、セットアップの種類、オプション機能のツリー、完了）が実行されます。サイレント インストールも従来どおり使えます（`msiexec /i 7-ZSTar-<version>-<arch>.msi /qn`）。サイレント モードでは、msiexecがUIシーケンス全体を省略するためです。ウィザードは英語のみで、別の言語に設定したWindowsでも同じです（繁体字中国語版Windows 10で確認。`.msi`は他の言語を含めずにビルドしています）。最後のページでは、*Launch 7-ZSTar File Manager*が既定でチェックされています。

### Windows 11の右クリックメニュー

Windows 11では、公式7-ZipやWinRARが今も置かれている*その他のオプションを確認*の奥ではなく、第1階層のメニューに項目が表示されます。Windows 11は、パッケージIDを伴うシェル拡張しかそこに載せないため、MSIはプログラムの隣に、IDだけを持つ小さなMSIXパッケージを同梱し、インストール中に登録します。従来の登録も残してあります。これは、メニューが1階層だけで*その他のオプションを確認*がないWindows 10とWindows 7で、右クリックメニューに項目を表示するもので、古いコンテキストメニューに戻した人の環境でも動作を保つものです。

そのパッケージは**自己署名証明書**で署名されており、インストーラーはその証明書を`LocalMachine\TrustedPeople`に入れます。信頼できるものにたどれない署名のパッケージを、Windowsは展開しないためです。アンインストールすると、パッケージと一緒に証明書も削除されます。Windows 10とWindows 7では、インストーラーはどちらも行いません。証明書を追加せず、パッケージも登録せず、従来の登録だけでメニューが提供されます。

自己署名証明書を信頼したくない場合は、その部分だけを断って、それ以外はそのまま使えます。

```
msiexec /i 7-ZSTar-<version>-<arch>.msi SPARSE=0
```

そうすると従来のメニューだけになるので、Windows 11では7-ZSTarの項目は右クリックメニューの*その他のオプションを確認*の中に表示されます。第1階層の項目をあとで有効にしたり、通常のインストールのあとで元に戻したりするには、次のようにします。

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -TrustCert -Register
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -Unregister -UntrustCert
```

その証明書を信頼するということは、同じ鍵で署名された**ほかのどんな**パッケージも、Windowsが警告なしに受け入れるということです。証明書はこの1つのパッケージにしか使いませんし、アンインストールすれば取り除かれますが、同意することになるのはそういう内容です。上の`SPARSE=0`が、それを断る方法です。

パッケージの登録はユーザーごとで、インストーラーはインストールした人に対してしか実行しません。その結果、次の2つのことが起きます。

- 同じコンピューター上の2つ目のアカウントは、同じスクリプトを`-Register`付きで実行するまで、従来のメニューだけになります。
- アンインストールで登録が解除されるのは、アンインストールした人の分だけです。ほかの人が登録していた場合、その人の登録はアンインストール後も残り、もう存在しないフォルダーを指します。そのアカウントは`Get-AppxPackage 7-ZSTar | Remove-AppxPackage`で消去してください。

**既知の制限：第1階層のメニューは、インストールが対話型でサインイン済みのセッションで行われたときにしか登録されません**。すべてのユーザー向けの`.msi`をリモートまたは非対話型のセッション（SSH経由や、管理ツールからのサイレント展開）でインストールすると、成功と報告されますが、Windows 11用のパッケージは登録されず、*その他のオプションを確認*の下の従来のメニューだけが表示されます。テストでは、SSHセッション（セッション0）からの`msiexec /i ... /qn`は終了コード0で終わりましたが、`Setup-ShellIntegration.ps1`は`registration failed: 0x80070005`（アクセスが拒否されました。）と報告しました。同じ`.msi`を管理者のコンソール セッションからインストールすると、正常に登録されました。

`-Status`は、何が設定され、何が設定されていないかを表示します。

### ユーザー単位のパッケージ

`7-ZSTar-<version>-<arch>-user.msi`は、現在のアカウントだけを対象に、`%LOCALAPPDATA%\Programs\7-ZSTar`へインストールします。ユーザー アカウント制御（UAC）の確認は表示されません。登録内容はすべて`HKCU`の下に入り、このパッケージは`HKLM`には何も書き込みません（Windows インストーラー自身の管理情報は除く）。コンピューター単位のパッケージと同じようにはできないこと：

- **Windows 11の第1階層のメニューはありません**。Windows 11では、7-ZSTarは右クリックメニューの*その他のオプションを確認*の中にあります。第1階層の項目には、自己署名証明書をコンピューター全体で信頼する必要があり、それには管理者が必要です。Windows 11で測定したところ、`CurrentUser\TrustedPeople`にある証明書だけでは、Windowsはパッケージを展開しません。そのため、ユーザー単位のパッケージでは省いています。
- **コンピューターごとに、2つのうち1つだけです**。各パッケージは、もう一方がインストールされている間はインストールを拒否します。もう一方をアンインストールしてから、インストールしてください。コンピューター単位のパッケージが検出できるのは、それを実行しているアカウントのユーザー単位のコピーだけなので、別のアカウントのユーザー単位のインストールは検出されません。
- **グループ ポリシーでメニューが隠されることがあります**。`EnforceShellExtensionSecurity`が設定されている環境では、エクスプローラーは、コンピューター全体の*Approved*キーに載っているシェル拡張だけを読み込みます。ユーザー単位のインストールはそこに書き込めないため、右クリックメニューは表示されません。そのような環境では、コンピューター単位のパッケージを使ってください。
- **ツール > オプション > システムで形式をクリアすると、7-ZSTarをその形式に提示する登録も削除されます**。そこで形式をクリアすると（セルが空になるまでクリックし、OKを押します）、ファイル マネージャーは`HKCU\Software\Classes\.<ext>`と`7-ZSTar.<ext>`のキーを丸ごと削除します。ユーザー単位のインストールでは、それらのキーに、パッケージが設定 > アプリ > 既定のアプリと*プログラムから開く*の一覧向けに登録した内容も入っています。その結果、その形式について7-ZSTarが*プログラムから開く*から消え、既定のアプリにはその形式の空のエントリが表示されます。インストールを修復すると元に戻ります（`.msi`をもう一度実行して*Repair*（修復）を選びます）。より良い方法は、ファイルの種類をファイル マネージャーではなく既定のアプリで割り当てることです。コンピューター単位のパッケージにも、1か所だけ同じ弱点があります。下のファイルの関連付けのところで説明します。

### ファイルの関連付けと、アンインストールで起こること

**設定 > アプリ > 既定のアプリで設定してください**。Windows 11では、そこで7-ZSTarと入力すると、開けるすべての形式が一覧表示されるので、割り当てられます。Windows 10では、7-ZSTarはそのページの*Set defaults by app*（アプリごとに既定値を設定する項目）の下に表示され、*Manage*（管理）でその形式を確認できます。Windows 7には設定アプリがありません。7-ZSTarは、コントロール パネル > 既定のプログラム > *既定のプログラムの設定*に表示され、このガイドの*既定のアプリ*は、そこではこれを指します。この2つのページからの形式の割り当ては、テストしていません。インストーラーは、7-ZSTarを既定のプログラムのアプリケーションとして登録します。形式ごとのProgID（アイコンと開くコマンド付き）、各拡張子の*プログラムから開く*の一覧への項目、Windowsが読むCapabilitiesブロックです。ただし、ファイルの種類は意図的に要求しません。どのプログラムでアーカイブを開くかはあなたが決めることで、それが7-ZSTarと公式7-Zipがお互いの邪魔をしない理由です。それでも、ほかにそれを開くと申し出るプログラムがないときは、Windowsが自分で形式を7-ZSTarに振り向けることがあります。テストしたWindows 10とWindows 7のマシンでは、ほかに`.7z`を登録したものがなく、`.7z`ファイルに7-ZSTarのアイコンが表示され、ダブルクリックで、どのプログラムを使うかをWindowsに尋ねられることなく、7-ZSTarで開きました。

**ファイル マネージャーの「ツール > オプション > システム」は、Windows 11ではほとんど機能しません**。これはWindowsの決まりであって、7-ZSTarの不具合ではありません。この画面は、`7-ZSTar.<ext>`というProgIDを`HKCU\Software\Classes`に書き込みますが、コンピューターがすでに知っている拡張子（アーカイブ形式はすべてそうです）については、Windows 11はそれを無視します。`AssocQueryString`は`Unknown`を返し、エクスプローラーは空白の汎用アイコンを表示します。Windowsが代わりに尊重するのは、Windowsだけが計算できるハッシュで署名された`UserChoice`キーで、そのため、そこでは設定のUIが唯一の経路です。どのアプリケーションもそれを書き込めません。7-ZSTarも、7-Zipも、どのインストーラーも同じです。Windows 10とWindows 7では、テストでの挙動が違いました。`.7z`と`.zst`をファイル マネージャーで設定し、ほかのプログラムを選んでいなければ、`AssocQueryString`はどちらも`7zFM.exe`を返しました。

**ファイル マネージャーの*すべてのユーザー*列で形式をクリアすると、コンピューター単位のパッケージ自身のその形式の登録が削除されます**。その列は`HKLM\Software\Classes`に書き込みます。コンピューター単位のパッケージは、そこに自分が提示するProgIDと*プログラムから開く*の項目を置いており、そこで形式をクリアすると（ファイル マネージャーを管理者として実行する必要があります）、それらのキーが丸ごと削除され、すべてのアカウントに影響します。ユーザー単位のパッケージでは、修復で同じキーが復元されました。こちらについては測定していません。

**何かを変更したあとも空白のままになるアイコン**は、エクスプローラーのアイコン キャッシュが原因のこともあります。このキャッシュは、すでにキャッシュしたDLLが置き換えられたことに気づきません。`ie4uinit.exe -show`でも確実には消去できません。エクスプローラーを終了し、`%LOCALAPPDATA%\Microsoft\Windows\Explorer\iconcache_*.db`を削除してから、もう一度起動してください。

**アンインストールでは、手の届く範囲の関連付けが削除されます**。対象は、アンインストールを行う人の`7-ZSTar.*`のProgIDと、まだそれを指しているファイルの種類だけなので、その間にほかのプログラムへ渡した形式はそのままです。コンピューター単位のパッケージのアンインストールは、ほかの場所にまだ存在する7-ZSTarのコピーを開くProgIDにも手を付けません。たとえば`.zip`からのポータブル版で、そのコピー自身の**ツール > オプション > システム**で設定したものです。ユーザー単位のパッケージにはそれができません。そのProgIDはまさにその`HKCU`のキー（上の*ユーザー単位のパッケージ*を参照）で、最後に誰が書いたかにかかわらず、アンインストールで削除されます。それらを残すと、アイコンとコマンドが削除済みの実行ファイルであるProgIDをそれらの種類が指すことになり、アイコンは空白、ダブルクリックするとエラーになります。ほかのアカウントの関連付けは手が届きません。そのアカウントは、プログラムが削除される前に`Setup-ShellIntegration.ps1 -RemoveAssociations`で自分の分を消去できます。`msiexec /x ... KEEPASSOC=1`はこの処理を省略し、アップグレードがこれを行うことはありません。

**既知の制限：ほかのアカウントは、自分で設定した関連付けを保持します**。コンピューター単位のパッケージのアンインストールで消去されるのは、アンインストールを実行したアカウントが、ファイル マネージャーの**ツール > オプション > システム**で自分の列（アカウント名の見出しの列）に設定したものだけです。ほかのアカウントがそこで設定した関連付けは、削除されたプログラムを指したまま残り、`.7z`ファイルをダブルクリックすると、Windowsがどのプログラムを使うか尋ねてきます。各アカウントは、アンインストールの**前に**、次のコマンドで自分の分を消去してください。

```
powershell -ExecutionPolicy Bypass -File "C:\Program Files\7-ZSTar\Setup-ShellIntegration.ps1" -RemoveAssociations
```

このコマンドは7-ZSTarの項目だけを削除します。あるいは、アンインストール後に、設定 > アプリ > 既定のアプリでもう一度種類を割り当て直してください。ファイル マネージャーで行う場合は、自分の列で7-ZSTarと表示されている各セルを、空になるまでクリックし、OKを押します。すべての行を選択して「+」を押さないでください。選択した行すべてに1つの状態が適用されるため、公式7-Zipなど、ほかのプログラムに属する形式までクリアされてしまいます。

**すべてのユーザー**列に設定した関連付けは、アンインストールのクリーンアップでまったく処理されず、そのままでは、すべてのアカウントが削除されたプログラムを指す状態が残ります。設定した管理者は、アンインストールの前に、管理者として実行したファイル マネージャーでそれらのセルをクリアし、OKを押してください。`-RemoveAssociations`はこの列には及びません。アンインストールの直前にクリアしても、そこにあるパッケージ自身の登録も削除される（上記）ものの、アンインストールでどのみち削除されるので問題ありません。ユーザー単位のパッケージには、ほかのアカウントの問題はありません。公式7-Zipも同じ動作です。

## 言語

すべてのパッケージには、上流の翻訳（90余りの言語）が入っています。言語は**ツール > オプション > 言語**で選びます。MSIでは、*Custom*セットアップで言語を含めないようにすることもできます。7-ZSTarは、初回起動時にシステムの言語に合わせようとしますが、Windowsの「Unicode 対応ではないプログラムの言語」と「地域設定」の内容が食い違うと、この検出は諦めて英語のままになります。言語を手動で選べば、常に動作します。

7-ZSTarが独自に追加した文字列（zstdのレベルと辞書のフィールド、新しいアーカイブ形式の名前）には、上流の翻訳がなく、英語のままです。例外は、バージョン情報ダイアログの**寄付**と**ウェブサイト**ボタンで、92言語のうち67言語にそれぞれの訳があり、残りの25言語では英語で表示されます（`Lang/UPSTREAM.md`にその一覧があります）。
翻訳は上流から取り込んだもので、ここで書いたものではありません。[Lang/UPSTREAM.md](../../Lang/UPSTREAM.md)を参照してください。
